# 교차 품질 (Cross-cutting Quality)

작업 유형과 무관하게, 변경이 아래 영역을 실제로 건드릴 때만 그 절을 적용한다. 각 절의 첫 줄이 트리거이고 마지막 `실패로 본다`가 그 절의 위험 신호다. 건드리지 않는 절을 형식적으로 채우는 것은 핵심을 흐리는 노이즈다. 되돌리기 어려운 선택(스택·도구·정책·비가역 릴리스)은 프로젝트 인텐트의 제약·결정 항목에 확인 날짜와 함께 남기고, 저장소별 실행 절차(파이프라인·환경·게이트 명령)는 운영 계약이 정본이다.

## 보안·하드닝

트리거: 신뢰 경계(외부 입력·인증·인가·비밀·외부 전송)를 건드릴 때. 심층 감사·시큐어 코딩·침투 테스트가 작업의 중심이면 메모리의 `audit-application-security`·`write-secure-code`·`run-authorized-penetration-test` 스킬로 전환한다.

- 기초 경계는 항상 유지한다: 인증, 서버 측 인가, 주입 방지, 비밀의 런타임 주입, 기존 데이터 보존, 기본 자격증명 금지. 이 경계는 개발 편의를 이유로 낮추지 않는다.
- 정책 차단은 진단 가능해야 한다. 인프라·플랫폼 정책(admission·웹훅·스키마·정규식)이 워크로드나 요청을 거절하면 어떤 정책이 어떤 값을 왜 거절했는지가 오류에 드러나야 한다. 정책 거절이 모델·런타임 장애로 오인되면 그것은 정책의 존재가 아니라 관측성 결함이다. 원인 불명의 차단은 먼저 정책 로그·감사 이벤트로 원인을 확정하고, 정책 자체를 끄는 것으로 진단을 대신하지 않는다.
- 정책 완화는 승인된 별도 변경이다. 개발 흐름을 막는 정책은 범위(로컬·POC·운영)와 완화 종류를 열린 질문으로 올리고 사람이 결정한다. 승인으로 제거된 정책은 일반 개선으로 되살리지 않고, 완화하지 않은 위험은 남는 위험으로 인텐트의 AI 판정 절에 적는다. 정책을 완화하면 게이트를 통과할 수 있다는 이유로 AI가 정책을 조용히 끄거나 우회하지 않는다.
- 릴리스 시점에 미완화 위험 목록을 보고한다. 방어 도입 여부와 깊이(비용·편의 대 보안)는 사람이 결정한다.
- 모든 외부 입력을 불신하되, 정상 경로를 막지 않는다. 경계 검증 시 사소한 포맷 변형은 계약이 허용하는 정규화(trim, 대소문자, 인코딩)로 수용한다. 자가 잠금 방지는 아래 관리·복구 경로 항목에 있다.
- 주입을 원천 차단한다. SQL·명령·경로·템플릿·헤더는 파라미터 바인딩·안전한 API·이스케이프로 만들고, 문자열 결합으로 쿼리·명령·경로를 만들지 않는다. 출력은 HTML·URL·JS·셸 각 맥락에 맞게 인코딩한다.
- 역직렬화·업로드·파서는 신뢰 경계다. 크기·타입·구조를 제한하고 안전한 파서를 쓴다.
- 인가는 매 요청 서버에서 확인한다. UI에서 감췄다는 이유로 생략하지 않고, 객체 수준 접근 통제(남의 자원 접근 불가)를 확인한다. 코드·토큰·프로세스·컨테이너는 최소 권한. 세션·토큰의 만료·회전·무효화를 처리한다.
- 비밀(키·토큰·비밀번호·인증서)을 코드·로그·에러 메시지·커밋에 넣지 않고 환경·비밀 관리자에서 주입한다. 로그·텔레메트리에 개인식별정보·자격증명·전체 본문을 남기지 않는다(필요 최소, 마스킹). 자체 암호를 발명하지 않는다.
- 안전한 기본값, 안전한 실패(fail-closed). 권한은 닫힌 상태에서 시작한다. 에러 메시지가 스택트레이스·경로·쿼리·버전을 외부에 노출하지 않게 한다.
- 고객·보안·자격증명·개인 데이터를 외부 AI·서드파티에 보낼 때는 필요성·승인·민감도를 먼저 판단하고(메모리 요구사항 `external-ai-data-handling`), 보낸 것은 캐시·색인될 수 있다고 전제한다.
- 관리·복구 경로는 살아 있어야 한다. 검증 실패나 닫힌 권한이 시스템 자가 잠금(Self-Bricking)으로 이어지지 않게 비상 복구 경로를 열어 둔다. 키 형식은 계약이 허용하는 Hex/Base64 정규화로 처리하되, 기존 데이터·세션 키를 임시 키나 임의 해시 파생값으로 조용히 교체하지 않는다. 키 오류는 해당 기능만 오류로 표시하고 별도 인증된 설정 복구 경로에서 원래 키 복원 또는 명시적 회전을 수행한다. 기존 데이터 읽기·재시작·롤백을 검증한다. 영속 데이터와 연결되지 않은 일회성 작업만 임시 키를 명시적으로 사용할 수 있다.
- 해당 방어에 회귀 테스트를 남기고, 저장소의 보안 게이트(의존성 audit·정적 분석)를 실측한다.

실패로 본다: 검증 없는 외부 입력, 문자열 결합 쿼리·명령, 클라이언트에만 있는 권한 검사, 로그·커밋의 비밀, 내부 구조를 노출하는 에러, 자가 잠금(Self-Bricking)을 유발하는 형식 결벽증 및 관리 복구 인터페이스 차단, 원인이 드러나지 않는 정책 차단, 승인 없이 끄거나 우회한 정책, 미완화 위험의 무보고.

## 복원력·관측성

트리거: 외부 의존성·비동기·상태 전이·실패 경로·사용자 흐름을 건드릴 때.

- 에러를 삼키지 않는다. `catch {}`로 무시하지 않고, 회복 가능(재시도) / 회복 불가(사용자 개입) / 프로그래밍 결함(크래시로 드러냄)으로 분류해 다르게 처리한다. 감쌀 때 원인·입력·위치를 붙여 원본 원인을 잃지 않는다.
- 모든 외부 호출(네트워크·프로세스·IO)에 타임아웃. 재시도는 회복 가능한 실패에만 지수 백오프와 상한을 두고, 비멱등 연산을 맹목적으로 재시도하지 않는다. partial output이나 side effect 뒤의 재시도가 중복을 만들지 않게 한다.
- 회로 차단·격벽으로 한 의존성의 실패가 전체를 무너뜨리거나 다른 기능의 자원을 고갈시키지 않게 한다. 비핵심 의존성이 죽어도 핵심은 살아 있고, 저하 상태를 사용자에게 사실대로 보인다(UX/UI 정본의 상태 계약).
- fail-closed는 경계된 폴백과 짝이다. 불변식을 지키려 정상 경로를 막을 때는 상한 있는 대기·저하 경로를 함께 설계해 무한 멈춤이 되지 않게 한다. 일시 장애를 actor·worker·job의 terminal 상태로 승격시키지 않고, 최종 실패 뒤에도 명시적 재개 경로를 남긴다.
- 외부에서 재시도될 수 있는 연산은 멱등하게 설계하거나 중복을 감지·차단한다. 부분 실패 후 상태가 일관되게 남고 다음 진입에서 복원·재개된다. 예외 흐름의 자원 해제는 플럼빙과 정합성 정본에 있다.
- 구조화 로깅: 검색·집계 가능한 구조, 상관관계 식별자(요청·세션·작업 id)로 한 흐름을 끝까지 추적, 의미에 맞는 레벨. 민감 데이터 금지.
- 소스코드 레벨 진단 로깅. 남길 항목은 진단과 디버깅 정본의 진단 로깅 절이 소유한다.
- 메트릭: 성공·실패율, 지연, 자원 사용, 큐 깊이처럼 상태를 판정할 수 있는 수치. 개선 주장 전에 측정 지점부터.
- 운영 중요 경로는 사용자 관점 SLI/SLO(가용성·p95/p99 지연·오류율)와 오류 예산을 정한다. 알림은 원인이 아니라 증상에(SLO 소진·오류율 급증), 사람이 행동할 수 있을 때만. 행동 불가·상시 발생 알림은 알림 피로를 만들므로 지우거나 고친다. 대시보드는 5초 안에 상태를 판정하게 한다.
- 실패 경로는 해피 패스만큼 검증한다. 실패를 일부러 주입해(fault injection) 방어가 실제로 동작하는지 확인하고 회귀 테스트를 남긴다.

실패로 본다: 삼킨 에러, 타임아웃 없는 외부 호출, 상한 없는 재시도, 폴백 없는 영구 차단, 상관관계 id 없는 로그, 추상 에러 메시지만 남는 진단, 원인 기반·행동 불가 알림, 검증 안 된 실패 경로.

## 데이터·마이그레이션

트리거: 스키마·저장 데이터·트랜잭션 경계를 건드릴 때.

- 데이터는 0.001%도 유실·변형되지 않게 방어한다. 파괴적 연산(삭제·덮어쓰기·컬럼 드롭·타입 변경) 전에 대상을 실제로 확인하고 복구 경로(백업·소프트 삭제·되돌리기)를 먼저 확보한다. 되돌릴 수 없는 이관은 사용자의 명시적 승인을 받는다.
- 확장 후 수축(expand → contract). 새 컬럼·테이블을 추가하고 코드가 양쪽을 읽게 한 뒤, 이관이 끝난 다음에야 옛 것을 제거한다. NOT NULL 추가·이름 변경·타입 변경 같은 깨지는 변경은 추가 → 이중 쓰기 → 백필 → 전환 → 제거의 다단계로 나눈다.
- 배포와 마이그레이션 순서를 맞춘다. 전개 창 동안 구버전 코드가 신버전 스키마에서, 신버전 코드가 구버전 스키마에서 동작하는지 확인한다.
- 마이그레이션은 멱등·재실행 안전. 큰 테이블은 잠금·부하를 고려해 배치·온라인으로. 실제 데이터 형태(대량·엣지 값)에서 검증하고 전진과 되돌리기를 모두 실측한다. 스키마를 바꾸면 그것을 읽는 모든 쿼리·타입·테스트를 같은 변경에서 맞춘다.
- 여러 쓰기가 원자적이어야 하면 트랜잭션으로 묶어 절반만 반영된 상태를 남기지 않는다. 분산 경계에서는 2단계 커밋 대신 saga·아웃박스·멱등 처리로 결과적 정합성을 설계하고 보상 경로를 명시한다. 동시 갱신은 낙관적/비관적 잠금·버전 필드로 lost update를 막고, 읽기-수정-쓰기 경합에는 원자 연산·조건부 갱신을 쓴다.
- 복구를 시험하지 않은 백업은 백업이 아니다. 보존·삭제 정책(개인정보 보존 기한 등)을 반영한다.
- 데이터 불변식(유일성·참조 무결성·상태 전이)을 회귀 테스트로 고정한다.

실패로 본다: 복구 경로 없는 파괴적 연산, 한 번에 바꾸고 지우는 스키마 변경, 배포·마이그레이션 순서 불일치, 되돌리기 미검증 마이그레이션, 부분 커밋 잔존, 조용히 이기는 마지막 쓰기, 복구 미검증 백업.

## 의존성·공급망

트리거: 의존성을 추가·갱신·제거하거나 스택을 고를 때.

- LTS·안정 버전을 기본으로, 검증된 최신을 쓴다. 버전은 시간에 민감하므로 현재 LTS·안정 최신을 검색해 확인하고 확인한 날짜를 남긴다. 갓 나온 major·프리릴리스·채택이 얕은 버전은 피한다. 업그레이드는 changelog·호환성·취약점 확인 후 한 번에 하나씩, 되돌릴 수 있게.
- 추가 전 판정: 표준 라이브러리나 기존 의존성으로 되면 추가하지 않는다. 몇 줄로 되는 일에 무거운 패키지, 기능 하나에 프레임워크 통째를 들이지 않는다. 유지보수 상태·채택 규모·라이선스·알려진 취약점을 확인하고, 방치·단독 유지·의심스러운 패키지를 피한다. 라이선스는 배포 조건과 호환을 확인하고 필요한 저작자 표시를 남긴다.
- 정확한 버전을 고정한다. 락파일(`package-lock.json`·`pnpm-lock.yaml`·`Cargo.lock`)을 커밋하고 범위 버전(`^`·`latest`)에 빌드를 맡기지 않는다. 의존성을 바꾸면 락파일을 같은 변경에서 갱신한다. 툴체인(런타임·컴파일러·빌드 도구)도 `.nvmrc`·`rust-toolchain.toml`·엔진 필드로 고정한다.
- 취약점 감사(`npm audit`·`cargo audit`·저장소 게이트)를 전이 의존성까지 실측 실행한다. 저장소 임계(예: high 이상 차단)를 따르고, 취약점은 억누르지 말고 갱신·대체·완화 중 근거 있는 조치를 남긴다.
- 쓰지 않게 된 의존성은 같은 변경에서 제거한다. 벤더링·패치(`patches/`)는 이유와 업스트림 상태를 남긴다.
- 설치 스크립트는 임의 코드를 실행할 수 있는 신뢰 경계다. 비밀·토큰을 패키지 설정·CI·레지스트리 인증에 노출하지 않고, 공개 배포물에 내부 레지스트리 경로가 새지 않게 한다.

실패로 본다: 기억 속 옛 버전 사용, 프리릴리스·미검증 최신 채택, 필요성 없는 추가, 라이선스 미확인, 범위 버전 빌드, 락파일 미갱신, 감사 미실행 또는 취약점 억제, 미사용 의존성 방치.

## 도입 판정·총소유비용

트리거: 새 의존성·프레임워크·도구·서비스·인프라·언어·패턴·추상화를 들일 때.

- 도입 비용은 설치 비용이 아니라 수명 전체의 비용(TCO)이다: 구현·정합, 학습·인지(저장소의 기술 수가 늘면 모든 후속 작업에 세금), 운영(업그레이드·패치·모니터링·요금), 정합(같은 문제에 두 해법이 공존하면 그 자체가 정합성 결함), 유지보수 부채(코드는 삭제될 때까지 영구 비용, 프롬프트·스킬·설정으로 풀면 0), 이탈 비용(깊이 얽힐수록 일방향 문).
- 복잡도 예산: 해법의 크기는 문제의 크기에 비례한다. 대안을 이 순서로 소거한다. (1) 아무것도 안 함 → (2) 프롬프트·스킬·지침·설정·기존 CLI 조합 → (3) 저장소의 기존 재료 → (4) 표준 라이브러리 → (5) 검증된 외부 도입 → (6) 필요한 최소만 직접 구현 → (7) 새 인프라·플랫폼(측정된 필요가 있을 때만). 앞 순번으로 풀리는 문제를 뒤 순번으로 풀면 실패다. 유행·이력서·새로움은 도입 사유가 아니다.
- 되돌리기 어려운 도입은 프로젝트 인텐트의 제약·결정 항목에 검토한 대안, 포기한 이유, 틀렸을 때 비용, 확인 날짜를 남긴다. 철회 계획을 도입 시점에 정한다. 철회 불가능한 도입은 일방향 문으로 승인 경계를 밟는다.
- 파급이 큰 도입은 한 모듈·한 흐름에서 파일럿한 뒤 확산한다. 새 것이 옛 것을 대체하면 옛 것을 같은 흐름에서 제거하고, 쓰이지 않게 된 도입은 제거한다.
- 이미 검증되어 잘 쓰이는 도입을 취향으로 걷어내는 것도 실패다. 판정은 도입할 때와 같은 TCO 기준으로 한다.

실패로 본다: TCO 없이 편의로 도입, 대안 소거 순서를 건너뛴 도입, 철회 계획 없는 되돌리기 어려운 도입, 파일럿 없는 전면 전환, 두 해법 공존 방치, 미사용 도입 방치.

## 릴리스·롤아웃

트리거: 변경을 배포·릴리스·공개할 때.

- 완료 계약을 먼저 통과한다. 모든 게이트 green, 완료 체크리스트의 이진 판정 통과, 비밀·공개 경계 확인이 전제다. 버전은 SemVer 의미에 맞게 올리고 모든 배포 표면(매니페스트·락파일·문서·이미지 태그)의 버전을 일치시킨다. changelog는 사용자 관점의 변화이지 커밋 로그 복사가 아니다.
- 비가역 마이그레이션·외부 발신·계약 공개가 포함되면 일방향 문으로 승인 경계를 밟는다.
- 롤백 경로가 없는 배포는 미완성이다. 롤백 계획을 릴리스 전에 정의하고 실측한다. "이전 버전 재배포"가 계획이면 설정·스키마·캐시가 구버전과 호환인지 확인한다. 검증 안 된 롤백은 롤백이 아니다.
- 파급이 큰 기능은 feature flag 뒤에 두어 배포(deploy)와 공개(release)를 분리하고, 문제 시 재배포 없이 끈다(kill switch). 사용자 영향이 큰 변경은 카나리·비율·링 배포로 일부에 먼저 내보내 관측한 뒤 확산한다. 전체 동시 전환은 전체 동시 장애다.
- 배포 완료는 릴리스 완료가 아니다. 배포 후 에러율·지연·핵심 흐름 성공률을 배포 전과 비교해 이상이 없음을 확인해야 끝난다. 이상이 보이면 원인 규명보다 복구(롤백·플래그 오프)가 먼저다.
- 교체 시 처리 중 요청을 드레인하고 종료 신호를 처리해 배포 자체가 오류·유실을 만들지 않게 한다.
- 롤아웃 완료 후 플래그·병행 경로·구버전 호환 코드를 제거하는 수축 작업을 계획한다. 영구히 남은 플래그는 분기 폭발·데드코드 부채다.

실패로 본다: 롤백 미정의·미검증 배포, 배포 후 관측 없는 완료 선언, 배포·마이그레이션 순서 불일치, 고파급 변경의 전체 동시 전환, 버전·표면 불일치, 커밋 로그 복사 changelog, 영구 플래그, 승인 없는 비가역 릴리스, 드레인 없는 교체.

## 성능 공학

트리거: 성능 개선이 목적이거나, hot 경로·대량 데이터·반복 외부 호출을 건드릴 때.

- 예산이 먼저다. p95/p99 지연, 처리량, 시작 시간, 메모리·CPU 상한, 번들·이미지 크기, 비용 상한을 위상 0의 제약으로 정하고, 검증 가능한 것은 게이트에 넣는다. 예산이 없으면 "느리다"도 "빨라졌다"도 판정할 수 없다. 주어지지 않았으면 사용자 관점(체감 지연·SLO)에서 제안하고 Ruling으로 남긴다.
- 프로파일링이 먼저다. 프로파일러·트레이스·메트릭으로 실측한 뒤 가장 큰 병목 하나부터 고친다. 코드를 읽고 짐작해 고치는 것은 금지다. 여러 곳을 동시에 바꾸면 무엇이 효과였는지 알 수 없다.
- 측정 조건을 통제한다: 같은 데이터 규모·환경, 워밍업 후, 여러 번 반복해 분산을 본다. 한 번 잰 수치는 수치가 아니다. 열 건에서 빠른 것이 백만 건에서 빠르지 않으므로 실제 형태·규모로 잰다.
- 흔한 원인: 불필요한 O(n²)·반복 안의 선형 탐색(차수 개선이 상수 최적화보다 크다), N+1 쿼리·반복 안의 네트워크 호출·chatty 동기 연쇄(배치·조인·일괄 조회·비동기 병렬), 과잉 fetch·과잉 렌더, hot 쿼리 인덱스 누락·실행 계획 미확인, 반복 직렬화·불필요한 복사·문자열 결합 반복, 락 경합·스레드 풀 고갈·독립 작업의 순차 실행.
- 캐시는 무효화·용량 상한·정합성과 함께 설계한다. 무효화 없는 캐시는 낡은 데이터 결함이고 상한 없는 캐시는 메모리 누수다.
- 운영 중요 경로는 예상 부하와 그 몇 배에서 부하 시험해 포화 지점을 알고, 연결 풀·메모리·큐 깊이의 상한을 명시해 상한에서 무너지지 않게 한다.
- 확정한 개선은 벤치마크·성능 테스트로 고정하고 예산을 게이트에 넣는다. 운영 메트릭으로 추세를 본다. 개발 환경 수치와 운영 수치는 다르다.
- 개선이 정확성·가독성·간결성을 해치면 대가를 명시하고, 예산 대비 의미 없는 이득이면 복잡도를 늘리지 않는다. 조기 최적화는 금지하되, 되돌리기 어려운 설계 결정(데이터 모델·동기/비동기·저장소 선택)은 처음에 옳게 한다.

실패로 본다: 예산 없는 성능 주장, 프로파일링 없는 추측 최적화, 단일 측정·조건 불일치 비교, 동시 다중 최적화, 무효화·상한 없는 캐시, 회귀 고정 없는 개선, 이득 없이 복잡도만 늘린 최적화, 소규모 데이터로만 검증.

## 설정·환경

트리거: 설정 키·환경변수·플래그·환경별 값을 추가·변경하거나 새 환경을 만들 때.

- 설정은 신뢰 경계의 입력이다. 시작 시 한곳에서 읽고 타입·범위·필수 여부를 검증해 실패하면 즉시 명확히 실패(fail-fast)한다. 누락값이 조용히 기본값으로 대체되어 운영에서 다른 동작을 하는 것을 금지한다. 검증된 설정은 타입 있는 객체로 전달하고, 코드 곳곳에서 환경변수를 직접 읽지 않는다.
- 출처(기본값 → 파일 → 환경변수 → 실행 인자)와 우선순위를 명시하고 문서화한다. 기본값은 단일 정본에 두고 코드·문서·예시 파일·배포 매니페스트에 복제하지 않는다. 예시 파일은 키 목록과 설명만 담고 실제 값·비밀은 담지 않는다. 설정 키에도 용어집의 공통 어휘를 쓴다.
- 환경 동등성: 로컬·CI·스테이징·운영은 설정값만 다르고 코드·의존성·빌드는 같다. 환경 이름으로 코드가 분기하면 운영에서만 도는 경로가 검증되지 않은 채 남는다. 실행 산출물이 버전·빌드 식별자를 스스로 보고해 낡은 빌드·이미지·캐시가 아님을 확인할 수 있게 한다.
- 로컬 환경은 재현 가능해야 한다. 새 사람이 문서대로 한 번에 게이트를 돌릴 수 없으면 그 부재가 결함이다.
- 비밀은 설정과 같은 통로로 읽되 저장은 분리하고(비밀 관리자·환경 주입), 설정 덤프·디버그 출력에서 마스킹한다.
- feature flag·동적 설정은 정의(어디에 어떤 플래그, 기본값)를 단일 정본에 두고 각 플래그의 소유자와 수축 시점을 남긴다. 런타임에 바뀌는 설정은 재로딩·재시작 필요 여부를 명시한다.

실패로 본다: 시작 시 검증 없는 설정, 누락값의 조용한 대체, 흩어진 환경변수 직접 읽기, 출처 우선순위 불명, 복제된 기본값, 환경 이름 분기 코드, 예시 파일의 실제 비밀, 재현 불가한 로컬 환경, 소유자·수축 계획 없는 플래그, 버전 미식별 산출물.

## 메모리·자원 효율

트리거: Rust·C·C++·Go·Zig 같은 시스템 언어, 임베디드, 고처리량·장기 실행 프로세스, 대량 데이터·hot 경로 코드를 쓰거나 고칠 때. 목표는 노는 메모리(idle memory)가 없는 코드다.

- 가장 짧은 수명, 가장 가까운 자리. 값은 필요한 범위에서 태어나 그 범위가 끝나면 죽는다. 수명을 늘리는 것은 실제 소비자가 그 밖에 있을 때만.
- 스택 우선. 힙 할당(`Box`·`Vec`·`String`·`HashMap`·`Arc`, `new`/`malloc`)은 크기가 가변이거나 수명을 호출자 밖으로 넘기거나 공유가 실제로 필요할 때만. "일단 힙에"는 소유권 설계를 미룬 것이다.
- 단일 소유자. 나머지는 빌린다. `Rc<RefCell<_>>`·`Arc<Mutex<_>>`·공유 포인터의 남발은 소유권 경계를 정하지 못했다는 신호이므로 먼저 누가 소유하는지 다시 설계한다.
- 복제 대신 빌림. `clone()`·`to_owned()`·`to_string()`·깊은 복사를 컴파일러가 시켜서 넣지 않는다. 빌림(`&T`·`&str`·`&[T]`)·이동·`Cow`로 먼저 해결하고, 복제 하나하나에 이유가 있어야 한다. 인자는 소유권이 필요 없으면 참조·슬라이스로 받는다. 문자열은 슬라이스·바이트로 다루고 포맷은 `write!`류로 기존 버퍼에 쓴다. 반복문 안의 `format!`·문자열 결합은 할당 폭탄이다.
- 스트리밍한다. 이터레이터 체인으로 흘려보내고 중간 `collect`·임시 리스트·전체 복사를 만들지 않는다. 대량 데이터는 청크·페이지로. 최종 크기를 알면 `with_capacity`·`reserve`로 한 번에 잡고, 모르면서 크게 예약하지 않는다(과대 예약이 노는 메모리의 주범). 다 쓴 큰 버퍼는 범위를 좁히거나 명시적으로 해제하고, `shrink_to_fit`은 측정된 필요가 있을 때만.
- 측정한다. 힙 프로파일러(heaptrack·dhat·pprof·valgrind massif), 할당 카운트, RSS 대 실제 사용량, `size_of`로 hot 구조체 크기를 본다. 흔한 원인: 과대 예약 capacity, 요청 뒤에도 유지되는 캐시·버퍼, 상한 없는 캐시·큐, `Arc` 순환 참조·잊힌 핸들, 전역 대형 테이블, 한 필드 때문에 통째로 살아 있는 큰 구조체. hot 구조체는 패딩을 보고 큰 enum variant·에러 타입은 `Box`로 감싸되, 측정된 hot 경로에서만 한다.
- 파일 핸들·소켓·연결·락·스레드·태스크도 같은 규율이다: 가장 짧은 수명, 명시적 상한(풀·세마포어), 실패 경로에서도 해제(RAII·`defer`·`finally`), 소유자 하나. 장기 실행 프로세스는 정상 상태에서 메모리·핸들이 평탄한지 시간 축으로 관측한다. 서서히 오르는 그래프는 누수다.
- `unsafe`·raw pointer·수동 메모리 관리는 마지막 수단이다. 지키는 불변식을 주석으로 문서화하고 sanitizer·miri로 검증하며 안전한 API로 감싼다. 임베디드·`no_std`는 정적 할당·고정 크기 버퍼·힙 없는 설계가 기본이다.
- 가독성을 해치는 미세 최적화는 금지다. 소유권이 명확하고 복제가 없는 코드는 대개 더 읽기 쉽다. 그 지점을 넘는 lifetime 곡예는 hot 경로에서 측정된 이득이 있을 때만. 관리형 언어(GC)에서는 할당보다 보유(retention)를 본다: 큰 그래프를 붙잡는 참조, 리스너·클로저 누수, 캐시 무한 성장.

실패로 본다: 이유 없는 `clone`·깊은 복사, 컴파일러를 달래려 넣은 복제·`Rc`/`Arc`, 소유권 설계 없는 힙 적재, 반복문 안 문자열 결합, 중간 컬렉션 연쇄, 과대 예약, 다 쓴 버퍼의 장기 보유, 상한 없는 캐시·큐, 측정 없는 "무거울 것" 수정, 실패 경로 자원 미해제, 불변식 문서·검증 없는 `unsafe`.

## 정책 디자인

트리거: 접근·한도·보존·과금·거버넌스 규칙을 도입·변경할 때. 이 절은 규칙을 무엇으로 정할 것인가를 다루고, 집행 기법은 보안·하드닝 절이, 보존·이관 구현은 데이터·마이그레이션 절이 맡는다.

- 정책이 코드 곳곳에 암묵적으로 흩어지면 서로 모순되고 누가 무엇을 할 수 있는지 아무도 단언하지 못한다. 한곳에서 명시적으로 정의하고 코드는 그 정의를 참조·집행한다. 되돌리기 어려운 정책 결정은 프로젝트 인텐트의 제약·결정 항목에 근거와 함께 남긴다.
- 권한·접근 모델: 주체·자원·동작의 매트릭스나 능력(capability) 목록으로 적는다. ad-hoc `if user.isAdmin`을 흩뿌리지 않는다. 자원 소유·테넌트 경계(객체 수준 규칙)를 정하고, 권한은 명시적으로 부여될 때만 열린다.
- 한도·쿼터·레이트 리밋: 사용자·테넌트·요금제별 한도(요청 수·저장량·동시성)와 초과 시 동작(거부 429·대기열·저하)과 사용자에게 알리는 방식을 정의한다. 조용히 실패시키지 않는다. 공정 사용·남용 방지 기준을 정한다.
- 보존·프라이버시: 보존 기간, 삭제 방식(soft/hard), 내보내기, 동의, PII 수집 최소화·마스킹·주체 권리(열람·삭제), 관할·규제 경계.
- 비즈니스 규칙·기본값: 허용된 상태 전이, 검증 규칙, 자격(entitlement)·과금 경계, 환불·유예·만료 정책을 검증 가능하게 적는다. "적절히 처리"가 아니라 "무료 요금제는 프로젝트 3개까지, 초과 시 생성 거부·업그레이드 안내".
- 거버넌스·감사: 누가 정책을 바꿀 수 있는가, 변경의 승인·재정의(override) 경로, 권한·한도·과금 변경의 감사 로그.
- 집행 지점: 권위 있는 검사는 서버 측이며 UI 감춤에만 의존하지 않는다. 여러 진입점에서 같은 정책이 일관되게 적용되고, 판정이 불확실하면 막는 쪽으로 실패한다.

실패로 본다: UI에만 있는 정책, 진입점마다 다른 집행, 정의 없는 암묵 규칙, 한도 초과 동작 미정의, 보존·삭제 정책 미정, 모델 없이 누적된 역할·권한, 정책 변경 감사 부재. 이미 명시적이고 일관되게 집행되는 정책은 보존한다.

## 국제 표준 준용

트리거: 모든 작업. 인증·규제 도메인(의료·금융·공공·개인정보)에서는 필수. 표준은 게이트를 대체하지 않고 게이트의 근거·용어·점검 항목을 제공한다. 프로젝트·규제가 특정 표준을 강제하면 그 강제가 우선한다.

> 표준 번호·판은 시간에 민감하다. 아래는 2026-08 기준이며, 인용·적용 전에 현행 판을 재확인한다.

| 방법론 영역 | 준용 표준 |
|---|---|
| 생애주기·프로세스 | ISO/IEC/IEEE 12207:2026, ISO/IEC/IEEE 15288 |
| 요구·인텐트 | ISO/IEC/IEEE 29148:2018(2024 재확인) |
| 제품 품질 모델 | ISO/IEC 25010:2023(9개 품질 특성), ISO/IEC 25012(데이터 품질) |
| 시스템·아키텍처 설계 | ISO/IEC/IEEE 42010:2022, IEEE 1016 |
| 테스트 전략 | ISO/IEC/IEEE 29119(1~5부) |

ISO/IEC 25010:2023의 9개 특성 대조: 기능 적합성 → 인텐트·요구 충족·테스트 전략, 성능 효율성 → 제약(예산)·성능 공학, 호환성 → 제약·API 계약, 상호작용 가능성 → UX와 UI·WCAG, 신뢰성 → 복원력·관측성, 보안 → 보안·하드닝, 유지보수성 → 도메인 모델링·코드 조직·리팩터링과 코드 품질, 유연성 → 설계·의존성·제약, 안전성(2023 신설) → 안전 필수 도메인에서 fail-closed·보안·정책으로 다루고 해당 도메인 표준을 추가 준용.

- 표준은 체크리스트를 풍부하게 만든다: 보안 심화는 ASVS의 검증 요구를, 테스트 조직은 29119의 프로세스를, 아키텍처 기술은 42010의 뷰·관점을 참조한다.
- 인용만 하고 형식적으로 만족하지 않는다. 실측·증거 게이트로 실제 준수를 확인한다. 방법론과 표준이 충돌하면 더 엄격한 쪽을 따르되 규제 강제 표준이 최우선이다. 심층 준수(인증·감사)는 전용 스킬·표준 원문으로 넘긴다.

실패로 본다: 현행 판 미확인 인용, 인용만 있고 실측 없는 준수 주장, 규제 강제 표준의 누락.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "내부용이라 보안은 나중에" | 기초 경계(인증·서버 인가·주입 방지·비밀 주입)는 개발 편의로 낮추지 않는다 |
| "정책이 막으니 잠깐 끄자" | 정책 완화는 승인된 별도 변경이다. 먼저 어떤 정책이 왜 막는지 로그로 확정한다 |
| "재시도를 넣으면 해결된다" | 상한·백오프·멱등성 없는 재시도는 중복 부작용과 장애 증폭을 만든다 |
| "마이그레이션은 한 번에 바꾸고 지우자" | 전개 창 동안 구·신 버전이 공존한다. 확장 후 수축으로 단계화한다 |
| "최신 버전을 기억하고 있다" | 버전은 시간에 민감하다. 공식 자료로 확인하고 날짜를 남긴다 |
| "이게 더 빠를 것이다" | 프로파일 없는 최적화는 추측이다. 같은 조건의 전후 수치로만 주장한다 |
| "롤백은 이전 버전 재배포면 된다" | 설정·스키마·캐시 호환을 확인하고 실측하기 전에는 롤백 계획이 아니다 |
