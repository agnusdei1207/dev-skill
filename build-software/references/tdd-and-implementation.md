# TDD와 구현 (위상 3)

구현 위상과 테스트 스위트의 모양을 소유한다. 핵심은 하나다: 실패하는 검증을 먼저 만들고, 그것을 통과시키는 최소 구현을 하고, 곧바로 정리한다. 검증이 앞서면 인텐트의 수용 기준이 코드로 고정되고, 나중에 회귀가 그 고정을 지킨다.

## 이음새(seam)를 먼저 정한다

- 테스트는 이음새에서만 쓴다. 내부 협력자·private 메서드는 테스트 대상이 아니다.
- 이음새는 구현 전에 정한다. 기존 이음새를 우선하고, 새 이음새는 가능한 한 높은 지점에 최소 개수로 둔다. 이음새의 정의와 모양(깊은 모듈·인터페이스)은 코드 조직 정본이 소유한다.
- 테스트 명령은 저장소가 쓰는 것을 먼저 확인한다. 기본 명령(`npm test` 등)을 추측해 돌리지 않고 운영 계약·매니페스트에서 실제 명령과 범위 지정 방법을 찾는다.
- 수용 기준 하나당 최소 한 테스트가 대응한다. 이 대응이 인텐트 충실도의 증거이며, 인텐트의 AI 판정 절에 테스트 이름으로 적힌다. 테스트 이름은 수용 기준과 용어집의 언어를 그대로 쓴다. "user can checkout with valid cart"처럼 사양으로 읽혀야 한다.

## RED → GREEN → REFACTOR

1. RED. 원하는 동작(기능) 또는 재현되는 결함(버그)을 기술하는 테스트를 쓰고, 실제로 실행해 실패를 확인한다. 실패 이유가 오타·환경 문제가 아니라 "미구현"인지 확인한다. 실패를 보지 않은 테스트는 무엇을 지키는지 알 수 없다.
2. GREEN. 테스트를 통과시키는 가장 작은 변경을 한다. 아직 필요 없는 일반화·추상화·기능을 넣지 않는다. 실행해 통과를 확인한다.
3. REFACTOR. 통과한 상태에서 중복 제거, 이름 명료화, 책임 분리, 죽은 경로 정리, 엣지 보강을 한다. 동작은 바뀌지 않으므로 테스트는 계속 green이다. 새 결함이 보이면 그 결함의 회귀 테스트를 먼저 만들고 고친다. 정리의 세부 규칙과 케이던스는 리팩터링과 코드 품질 정본이 소유한다.

한 태스크 안에서도 이 사이클을 여러 번 돌려 목표로 수렴한다.

### 수직 슬라이스와 예광탄

- 수평 분할을 금지한다. 테스트를 전부 먼저 써 두고 구현을 몰아서 하는 방식은 상상 속 행위를 검증할 뿐이고, 구현을 배우기 전에 테스트 구조에 손발이 묶인다.
- 수직 슬라이스로 전진한다. 한 번에 하나의 이음새, 하나의 테스트, 하나의 최소 구현. 각 테스트는 직전 사이클이 가르쳐 준 것에 반응하는 예광탄(tracer bullet)이다.

### 테스트 안티패턴 3대 금기

1. 구현 결합. 내부 협력자를 과도하게 mock하거나, private을 직접 테스트하거나, 사이드 채널(DB 직접 조회)로 검증한다. 징후: 동작은 그대로인데 리팩터만으로 테스트가 깨진다.
2. 동어반복. 코드가 계산하는 방식을 단언에서 그대로 다시 계산한다(`expect(add(a, b)).toBe(a + b)`). 구조상 절대 실패할 수 없다. 기댓값은 사양·검증된 리터럴·실측값 같은 독립된 진실에서 나와야 한다.
3. 가짜 안도감. 실제 결함이 요구하는 복합 호출 체인을 흉내 내지 못하는 얕은 단위 테스트에 만족한다. 올바른 이음새가 아니면 통합·계약 층위로 올린다.

## 근본 원인 수정 (버그픽스)

근본 해결은 그 문제가 다시 생기지 않게 닫는 것이다. 세 가지가 모두 참일 때 성립한다: (1) 원인을 데이터 모델·아키텍처·계약 층위에서 고쳤고, (2) 같은 원인이 사는 인스턴스가 아니라 클래스 전체(모든 인접 경로)를 닫았고, (3) 그 불변식을 회귀 테스트로 영구 고정했다.

- 버그는 먼저 재현한다. 원인 확정은 진단과 디버깅 정본의 절차를 따르고, 확정된 원인을 드러내는 실패 테스트에서 RED를 시작한다.
- 스택트레이스의 마지막 줄만 막지 말고, 잘못된 값·상태가 어디서 처음 생겼는지까지 배선을 거슬러 올라간다.
- 가능하면 잘못된 상태 자체를 타입·불변식으로 표현 불가능하게 만들어 그 부류의 버그가 애초에 컴파일되지 않게 한다.
- 금지: 하드코딩 패치, 조건 우회, 예외 삼키기(`catch {}`), 타임아웃·재시도로 경합 덮기, 테스트만 통과하도록 값 맞추기.
- 마감은 회귀 테스트가 남고, 파급된 정합성이 맞춰지고(플럼빙과 정합성 정본), 임시·디버그 산출물과 데드코드가 사라졌을 때 끝난다.

## 최소 구현과 재사용

- 가장 작은 설계를 택한다. 능력을 보존하면서 소유권이 분명하고 검증하기 쉬운 최소 설계로, 새 코드를 더하기 전에 기존을 삭제·단순화할 수 있는지 먼저 본다. 지금 필요 없는 기능·설정·추상화·래퍼 계층을 "나중을 위해" 넣지 않는다(YAGNI). 근거가 되는 철학은 방법론 정본 0절이 소유한다.
- 검증된 것을 재사용한다. 같은 일을 하는 primitive·유틸·컴포넌트가 있으면 새로 만들지 않는다. 재사용 전에 그 계약이 이 용도에 맞는지 확인한다. 두 번째 사본이 생기면 공통을 뽑되, 서로 다른 것을 억지로 묶지 않는다(컴포넌트와 재사용 정본).
- 프레임워크·라이브러리 API는 기억이 아니라 공식 문서와 설치된 버전으로 확인한다. 버전마다 시그니처·기본값·폐기 여부가 다르며, 확인하지 않은 API 사용은 가정이다.

## 책임 분리와 타입

- 경계는 주입 가능한 인터페이스로 노출해 소비자가 구현을 교체·mock할 수 있게 하고, 프리플라이트에서 약속한 생산자→소비자 계약이 코드에 나타나게 한다. 책임을 어디서 나누는지는 코드 조직 정본의 관심사 분리가 소유한다.
- 잘못된 상태를 표현 불가능하게 만든다. 배타적 필드 조합, 문자열로 흉내 낸 상태값, "null이면 아직 없음" 대신 enum·유니온·상태 타입으로 허용된 상태만 표현한다.
- 경계에서 parse하고 내부는 신뢰한다. 외부 입력은 신뢰 경계에서 한 번 검증해 타입 있는 값으로 바꾸고, 내부는 그 타입을 믿는다. 안쪽에서 같은 값을 반복 검증하는 것은 경계가 어디인지 모른다는 신호다.
- 단위 타입을 쓴다. 금액·시각·식별자·경로처럼 섞이면 안 되는 값을 원시 타입으로 돌리지 않는다. 금액·시각의 표현 기준은 설계 정본의 데이터 모델 절에 있다.
- null·옵션과 수량을 타입으로 고정한다. 없을 수 있는 값은 타입으로 드러내고, 하나인가 여럿인가(0..1 / 1 / 0..N / 1..N)를 타입이 말하게 한다. 도메인상 여럿이 가능한 것을 단일 값 타입으로 두지 않는다. 이름과 수량의 일치는 식별자·문구·주석 정본이 소유한다.
- 정적 타입이 없는 언어에서는 스키마 검증·런타임 단언·문서화된 계약으로 같은 효과를 낸다.

## 구현 중 배선 인식

값을 새로 만들거나 옮길 때 그 값의 생산자와 모든 소비자를 그 자리에서 확인한다. 새 필드를 추가하면 읽어야 할 모든 곳을, 제거하면 읽던 모든 곳을 같은 변경에서 처리한다. "나중에 배선하겠다"는 소비자 없는 생산자를 남긴다. 전수 추적은 플럼빙과 정합성 정본이 소유한다.

## 동시성·자원 안전

- 공유 상태 접근은 경합·교착·락 오염을 고려한다. 락은 좁게 잡고, 락을 든 채 오래 걸리는 작업을 하지 않는다.
- 실패 경로의 자원 해제는 플럼빙과 정합성 정본의 종료·정리 수명주기를 따른다.
- 취소·인터럽트 지점에서 부분 상태가 남지 않게 하거나, 남더라도 다음 진입에서 안전하게 복원되게 한다.

## 테스트 스위트의 모양

- 수준. 단위(빠르고 격리된 로직·규칙·엣지, 가장 많이), 통합(경계가 실제로 맞물리는지, 가능한 한 실제 의존성으로), 계약(생산자·소비자가 인터페이스 약속을 지키는지, 계약이 바뀌면 먼저 깨진다), E2E(핵심 사용자 여정 몇 개만), 속성 기반·스냅샷(불변식은 속성으로, 렌더·직렬화는 무엇을 지키는지 알고 스냅샷으로).
- 피라미드. 빠른 단위·통합이 많고 느린 E2E는 적게. 각 수준은 자기가 가장 잘 잡는 결함을 잡게 배치한다. 로직 버그를 E2E로, 배선 버그를 단위로 잡으려 하지 않는다.
- 무엇을. 동작·계약·불변식·엣지 케이스를 공개 계약으로 검증한다. 실패 경로를 해피 패스만큼 테스트한다. 자명한 getter, 프레임워크 자체, mock을 세워 mock을 단언하는 테스트는 만들지 않는다.
- 행위 전체를 반증한다. 상태·비동기·전달·영속이 있는 경로는 값 하나가 아니라 사용자 행위 하나의 전체 수명주기를 통째로 반증한다. 첫·마지막·high-water mark만 맞는 테스트는 중간 hole·중복 소비·부분 성공을 놓치므로 정확한 cardinality·그룹 전체·순서·중복을 단언한다. 성공만이 아니라 실패·취소·포화·재시작 전이를 각각 고정한다. 상태가 남아 있음(존재)과 새 activity가 발생함(발생)을 구분하고, 같은 revision이 한 번만 소비됨을 단언한다. 상한 초과 입력은 framing·decode·인자·queue·결과·투영 각 지점에 넣어 부작용 전에 거부되는지 확인하고, deadline은 행위 전체로 만료시켜 본다.
- 격리와 결정성. 픽스처는 현실적이되 최소로, 서로 격리되게. 시간·네트워크·순서·경합에 의존하지 않는다. 불안정한 테스트는 고장난 테스트다. 고치거나 지운다.
- 커버리지는 목표가 아니라 신호다. 핵심·엣지 경로를 덮었는지를 보고, 숫자를 맞추려 무의미한 테스트를 만들지 않는다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "코드가 돌아가면 테스트를 쓰겠다" | 나중에 쓴 테스트는 행위가 아니라 구현을 확인하고, 대개 쓰이지 않는다 |
| "너무 단순해서 테스트할 게 없다" | 단순한 코드도 자란다. 테스트는 기대 동작의 사양으로 남는다 |
| "손으로 확인했다" | 수동 확인은 남지 않는다. 내일의 변경이 그것을 깨도 알 방법이 없다 |
| "테스트가 처음부터 통과했다" | 실패를 보지 않은 테스트는 무엇을 지키는지 모른다. RED를 먼저 본다 |
| "버그는 원인이 분명하니 바로 고친다" | 재현 테스트 없는 수정은 고쳤다는 증거가 없고 회귀를 막지 못한다 |
| "mock하면 빠르다" | 내부 협력자 mock은 리팩터 때마다 깨지고 실제 배선 결함을 숨긴다. 이음새에서만 대체한다 |
| "확실히 하려고 한 번 더 돌리자" | 코드가 바뀌지 않았으면 같은 명령의 재실행은 정보가 없다. 간헐성을 의심하면 반복 횟수를 정해 재현율을 잰다 |

## 위험 신호

- 대응 테스트 없는 새 동작, 실패를 보지 않은 테스트, 처음부터 통과한 테스트
- 저장소 명령을 확인하지 않은 기본 테스트 명령, 실제로는 0개가 실행된 "전부 통과"
- 이음새 밖 테스트, 수평 분할, 구현 결합·동어반복·가짜 안도감
- 재현 테스트 없는 버그 수정, 증상만 가린 수정, 인접 경로 미감사
- 스킵·비활성화된 테스트로 만든 초록, 불안정 테스트 방치, 실패 경로 미검증
- 조기 추상화·불필요한 계층, 원시 타입 금액·시각, 단수로 설계된 다수 개념, 역피라미드
- 기억에 의존한 프레임워크 API 사용

## 종료 게이트

- [ ] 새 동작마다 RED를 관측했고, GREEN을 저장소 명령으로 실측했고, REFACTOR로 정리했다
- [ ] 버그 수정은 수정 전에 실패한 재현 테스트가 있다
- [ ] 수용 기준마다 대응 테스트가 있고, 테스트 이름이 기대 행위를 용어집 언어로 말한다
- [ ] 스킵·비활성화된 테스트가 없다(있다면 이유와 함께 보고)
- [ ] 새로 만든·옮긴 값의 생산자와 모든 소비자를 확인했다
