# 자원 회수 (Resource Reclamation)

도커·Compose 빌드/테스트와 임시 작업이 남기는 자원의 수명과 회수를 소유한다. 여기서 다루는 것은 일회성 자원이다. 영속 데이터·볼륨의 보존·삭제는 [데이터·마이그레이션](cross-cutting-quality.md) 절이 소유하고, 코드의 자원 해제는 [플럼빙과 정합성](plumbing-and-consistency.md)이 소유한다. 자원을 만든 주체가 같은 변경에서 회수할 책임을 진다. "나중에 정리"는 정리가 아니다.

## 절차

1. 시작 전 스냅샷을 남긴다. `docker ps -a`, `docker images`, `docker volume ls`, `docker network ls`, `docker system df`와 작업 디렉터리의 임시 파일·브랜치·워크트리를 기록한다. 이미 있던 자원과 이번 작업이 만들 자원을 구분한다.
2. 태스크 자원에 소유자를 붙인다. Compose는 프로젝트 이름(`name:` 또는 `--project-name`)을, 단발 컨테이너·이미지·네트워크·볼륨은 태스크 식별자가 들어간 이름과 라벨을 쓴다. 소유자 식별이 없으면 나중에 무엇을 지워도 되는지 증명할 수 없다.
3. 만들 때 회수 비용을 같이 정한다. 상한(메모리·CPU·디스크), `--rm`, `tmpfs`, 명시적 빌드 캐시 경로, 호스트 스크래치 경로를 먼저 정하고 성공 경로에만 정리 코드를 두지 않는다.
4. 모든 종료 경로에서 정리한다. 성공·실패·타임아웃·인터럽트에서 같은 정리 경로를 탄다(shell `trap`, `finally`, CI `post` step). 태스크가 만든 컨테이너·네트워크·이미지·스크래치 파일을 제거하고, `docker compose down --remove-orphans`로 프로젝트 자원을 내린다.
5. 종료 후 스냅샷을 다시 떠서 시작 전과 대조한다. 태스크가 만든 항목이 0건인지 확인하고, 남아 있으면 소유자·유지 이유·다음 정리 시점을 기록한다.
6. 보고에 회수한 자원 종류·개수·디스크 회수량(`docker system df` 전후)과 의도적으로 남긴 영속 자원과 근거를 붙인다.

```bash
# 시작 전/후 대조에 쓰는 최소 스냅샷
docker ps -a --format '{{.Names}} {{.Image}} {{.Status}}'
docker images --format '{{.Repository}}:{{.Tag}} {{.ID}}'
docker volume ls
docker network ls
docker system df

# 태스크 소유 자원만 지우는 예 (라벨/이름으로 범위를 좁힌다)
docker compose --project-name <task-id> down --remove-orphans
docker rm -f <task-id>-*
docker image rm <task-id>-image
docker builder prune --filter 'label=<task-id>'
```

## 판단 기준

- **일회성과 영속을 먼저 구분한다.** 빌드 컨테이너·중간 이미지·임시 네트워크·스크래치 파일·임시 브랜치는 회수한다. 이름붙인 볼륨, 모델 캐시, DB 데이터, 공유 이미지 레이어는 작업이 만들지 않았으면 지우지 않는다. 컨테이너를 내리는 것과 볼륨을 지우는 것은 다른 행위다.
- **광역 정리 명령은 승인 대상이다.** `docker system prune -a`, `docker image prune -a`, `docker volume prune`, 저장소 전체 `git clean -fdx`는 범위가 태스크를 넘는다. 승인 없이 쓰지 않고, 써야 하면 대상과 영향을 먼저 확인한다.
- **캐시는 무제한으로 쌓지 않는다.** 반복 작업에서 캐시가 이득이면 상한·만료·라벨 필터로 유지하고, 이득이 없으면 만든 곳에서 지운다. 캐시가 있다는 이유로 정리를 생략하지 않는다.
- **실패한 작업이 더 위험하다.** 실패·취소 경로에서 남은 자원이 다음 실행을 막거나 디스크를 계속 먹는다. 정상 경로만 성공한 정리는 불완전하다.
- **영속 자원을 지워야 할 때는 명시적 승인을 받는다.** 데이터·마이그레이션 절의 파괴적 연산 규칙을 따르고, 복구 경로를 먼저 확보한다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "나중에 한 번에 정리하자" | 누적된 자원은 소유자를 잃고, 어느 것이 안전한지 판단할 수 없게 된다 |
| "컨테이너를 내렸으니 끝이다" | exited 컨테이너·중간 이미지·빌드 캐시·임시 볼륨이 남는다. 스냅샷 대조가 증거다 |
| "도커가 알아서 정리한다" | 도커는 미사용 자원을 자동 삭제하지 않는다. 소유자가 회수 경로를 정의해야 한다 |
| "prune 한 번이면 편하다" | 광역 prune은 남의 이미지·영속 볼륨까지 지운다. 범위를 태스크로 좁힌다 |
| "볼륨을 지워야 용량이 줄어든다" | 영속 볼륨과 일회성 자원을 혼동하면 복구 불가능한 데이터 삭제가 된다 |
| "캐시가 있으니 다시 정리할 필요 없다" | 상한 없는 캐시는 계속 자란다. 유지하면 상한을 정하고, 아니면 회수한다 |
| "성공했으니 정리됐다" | 성공 경로만 정리했을 수 있다. 실패·취소 경로도 같은 스냅샷 대조를 통과해야 한다 |

## 위험 신호

- 태스크 종료 뒤 `docker ps -a`에 exited 컨테이너가 남거나 `docker images`에 `<none>` 중간 이미지가 쌓임
- 반복 작업마다 `docker system df`가 단조 증가, 빌드 캐시가 계속 커짐
- 영속 볼륨·모델 캐시·DB 데이터가 "정리"로 사라졌거나, 사라질 뻔함
- 정리 명령이 성공 분기에만 있고 실패·취소 분기에는 없음
- 자원 이름에 소유자가 없어 무엇을 지워도 되는지 단언할 수 없음
- 광역 prune을 습관적으로 실행, 승인·대조 기록 없음

## 종료 게이트

- [ ] 시작 전·종료 후 스냅샷을 대조했고 태스크 소유 일회성 자원이 0건이다
- [ ] 성공·실패·취소·인터럽트 경로에서 정리가 실행됐음을 확인했다
- [ ] 영속 볼륨·캐시·공유 이미지는 식별해 보호했고, 삭제했다면 승인과 복구 경로가 있다
- [ ] 승인 없는 광역 prune·넓은 범위 정리를 쓰지 않았다
- [ ] 회수량과 의도적으로 남긴 자원·이유를 보고에 남겼다
