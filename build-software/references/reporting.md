# 사람 보고

이 파일은 사람에게 어떻게 보고하는가만 소유한다. 무엇을 문서로 남기는가는 인텐트 정본이, 읽기 쉬운 글을 쓰는 법은 저장소 공통 스킬 `write-readable-text`가 소유한다. 사람이 읽는 시간이 곧 비용이므로 보고는 압축하고, 설계적인 부분을 중심에 둔다.

## 무엇을 앞에 두는가

보고의 머리에는 결정과 그 근거를 둔다. 파일별 diff 나열이나 편집 로그가 아니다.

- 무엇이 되었나 — 결정 수준으로. (예: "provider 경계를 주입식으로 분리해 UI 재작성 없이 교체 가능하게 했다")
- 왜 그렇게 했나 — 핵심 트레이드오프와 포기한 대안.
- 무엇이 검증됐나 — 증거를 수치로 압축. (예: "전체 게이트 10/10 통과, 테스트 528개") 로그 전문을 붙이지 않는다.
- 무엇이 남았나 — 블로커·가정·불확실성. 정직하게, 짧게.

## 독자는 정책을 결정하는 사람이다

- 추상 레벨을 지킨다. 설계·정책 레벨(무엇을 얻고 무엇을 포기하는가)로 쓴다. 파일명·메서드명·내부 변수 같은 구현 세부는 본문에 올리지 않는다. 그것은 코드와 인텐트의 AI 판정이 소유하고, 보고는 필요할 때 인텐트 번호만 가리킨다.
- 쉬운 말로 쓴다. 도메인을 모르는 사람이 한 번 읽고 이해하는 문장. 전문 용어는 꼭 필요한 것만, 처음 등장할 때 한 줄로 풀이. 작업 중 만든 코드네임·약어를 설명 없이 쓰지 않는다.
- 질문은 결정 요청으로 만든다. "어떻게 할까요?" 대신 선택지 + 각각의 트레이드오프 + 추천을 제시해 사람이 고르기만 하면 되게 한다. 이 형식 그대로 인텐트의 `열린 질문`에 남긴다.
- 묻는 것은 정책이지 구현이 아니다. 구현 방법은 스스로 정한다. 사람에게는 제품 판단·트레이드오프·일방향 문만 가져간다.

## 압축 규칙

- 결정 > 과정. 어떤 순서로 무슨 파일을 열었는지는 필요 없다.
- 수치로 압축. "많은 테스트가 통과했다" 대신 "47/47 통과". 원문 로그는 요청 시에만.
- 중복 판단 제거. 같은 사실은 한 번, 가장 정확한 자리에서.
- 스캔 가능하게. 짧은 단락과 필요한 만큼의 항목. 항목을 위한 항목은 만들지 않는다.
- 정답처럼 단정하지 않는다. 판단에는 근거와 범위를 붙이고, 확인한 사실과 가정을 구분한다.

## 보고 골격

```text
<한 줄 결론: 무엇이 되었는가>

설계: 핵심 결정과 근거 (2~4줄, 트레이드오프 포함)
검증: 실행한 게이트와 결과 수치
남은 것: 블로커·가정·다음 단계·사람 결정거리 (있을 때만)
```

작은 작업은 한두 문장으로 압축한다. 큰 작업도 이 순서를 유지하되 각 줄을 늘리지 않는다. 길이는 작업 크기가 아니라 사람이 결정을 이해하는 데 필요한 최소량이 정한다. 보고는 인텐트의 AI 판정을 요약하고 가리키지, 복제하지 않는다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "한 일을 다 보여 줘야 성실해 보인다" | 사람의 시간은 비용이다. 결정과 근거, 수치, 남은 것만 앞에 둔다 |
| "실패는 굳이 말하지 않아도 된다" | 숨긴 실패는 사람이 코드를 열게 만든다. 그것이 이 방법론의 실패다 |
| "어떻게 할까요?" | 선택지·트레이드오프·추천이 없는 질문은 결정을 사람에게 떠넘긴 것이다 |

## 위험 신호

- 파일별 diff 나열·편집 로그로 시작하는 보고, 로그 전문 첨부
- 설명 없는 코드네임·약어, 구현 세부가 본문을 채움
- 수치 없는 "많이 통과", 확인한 사실과 가정의 혼재
- "하겠다/알려 달라"로 끝나는 미완의 약속

## 종료 게이트

- [ ] 첫 줄이 결론이고, 설계·검증·남은 것 순서다
- [ ] 검증은 실행한 게이트와 수치로, 실패·미검증·건너뜀이 분리돼 있다
- [ ] 사람에게 묻는 것은 선택지·트레이드오프·추천을 갖춘 결정 요청뿐이다
