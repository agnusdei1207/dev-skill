# 컴포넌트와 재사용

이 파일은 같은 것이 한 번만 존재하게 하는 규율을 소유한다: 재료 우선과 조립, 중복 금지와 추출 시점, 단일 정본 상수·enum, 리터럴 감사, 디자인 토큰, 컴포넌트 기반 개발(Component-Based Development, CBD). 공용 코드를 어느 폴더에 두는가는 코드 조직 정본이, 화면의 상태·접근성 계약은 UX/UI 정본이 소유한다.

## 절차

1. 만들기 전에 재고를 검색한다. 공유 컴포넌트·모듈·유틸·훅·토큰·타입·enum·상수·primitive·표준 라이브러리에서 같은 역할을 찾는다.
2. 있으면 계약이 이 용도에 맞는지 확인하고 쓴다. 조금 모자라면 계약을 확장하고 기존 소비자를 전부 이전한다.
3. 없으면 다음에도 조립할 수 있는 형태로 만든다. 이 자리에서만 쓰는 일회성 모양을 피한다.
4. 변경 종료 전에 리터럴 감사와 중복 검색을 돌린다.

## 재료 우선·조립·중복 금지

- lib으로 되는 것을 재발명하지 않는다(새 의존성 판정은 교차 품질 정본). 대부분의 작업은 재료 제작이 아니라 조립이어야 한다.
- 같은 로직·같은 UI는 한 번만 존재한다. 두 번째 사본이 생기는 순간이 추출 신호다. 복사-붙여넣기는 결함이다. 차이는 사본이 아니라 파라미터·variant로 표현한다.
- 성급한 공통화도 금지. 우연히 비슷할 뿐 변경 이유가 다른 둘을 억지로 묶지 않는다. 추출은 두 번째 실재 반복에서.
- enum·상수·상태값·타입은 단일 정본. 같은 상태 목록을 여러 파일에 다시 선언하지 않는다. 문자열로 상태를 흉내 내지 않는다.
- 리터럴 감사. 자명한 것(0, 1, -1, 빈 문자열, 단위 변환) 외의 숫자·문자열·URL·경로·키·정규식·시간값·색상값은 이름 있는 상수·enum·설정·토큰으로 뽑는다(`3600` 대신 `SECONDS_PER_HOUR`, `"pending"` 대신 상태 enum). 매직 문자열 분기(`if kind == "admin"`)는 타입 안전을 버린 것이다. 변경 종료 전 diff의 리터럴을 전수(grep)해 남은 것마다 이유를 답할 수 있어야 한다.
- 디자인 토큰. 색·간격·타이포·라운드·그림자·모션은 토큰으로 중앙화하고 정해진 스케일을 따른다. 화면에 `#3b82f6`·`13px`를 흩뿌리지 않는다. 변형은 fork가 아니라 prop·variant로, 표현과 로직은 분리한다.

## 컴포넌트 기반 개발(CBD)

컴포넌트는 반복 마크업을 감싼 함수가 아니라, 한 사용자 개념의 구조·상태·행동·접근성·시각 규칙을 한곳에서 소유하는 조립 단위다. 페이지는 컴포넌트를 배치하고 도메인 상태를 전달할 뿐, 같은 제어를 다시 구현하지 않는다.

- 재고부터 시작한다. 화면을 바꾸기 전에 기존 컴포넌트·primitive·토큰과 모든 소비자를 검색한다. 맞는 계약이 있으면 확장해 전 소비자를 이전하고, 같은 역할의 두 번째 구현을 만들지 않는다.
- 소유자는 하나다. 버튼·입력·선택·탭·메뉴·대화상자·drawer·toast·표·검색·빈 상태·로딩 상태마다 구조, 접근 가능한 이름, keyboard·pointer·focus 수명주기, disabled·loading·error 상태, 반응형과 테마를 소유하는 정본 컴포넌트를 하나 둔다. CSS selector와 이벤트 위임도 그 경계를 따른다.
- 계약으로 변형한다. 실제 의미 차이는 이름 있는 `variant`·size·state·slot·callback으로 표현한다. 화면 경로·DOM 조상·임의 클래스에 따라 같은 컴포넌트가 몰래 달라지게 하지 않는다. boolean prop이 늘어 조합 불가능 상태를 만들면 의미 있는 variant나 별도 컴포넌트로 나눈다.
- 상태와 표현을 분리한다. 도메인·서버 상태의 소유자는 container/controller 한 곳이며 표현 컴포넌트는 입력과 이벤트 계약만 받는다. 컴포넌트 내부 임시 상태는 열림·포커스·초안처럼 자기 수명주기에 한정하고, 같은 상태를 DOM·전역·서버에 중복 소유하지 않는다.
- 조합이 상속보다 먼저다. 작은 primitive를 slot과 명시적 자식 구조로 조립한다. 모든 경우를 아는 거대 컴포넌트, 화면별 조건문이 누적된 공용 컴포넌트, 스타일만 전달하는 패스스루 래퍼를 만들지 않는다.
- 추출과 분리를 증거로 결정한다. 같은 의미·행동의 두 번째 사본이 생기면 공통 컴포넌트로 추출한다. 겉모습만 비슷하고 상태·행동·변경 이유가 다르면 토큰만 공유하고 별도 컴포넌트로 둔다.
- 우회를 금지한다. 화면 파일의 raw 버튼·입력·SVG, 페이지 한정 색·간격·hover CSS, 문서 전역의 임시 click/keydown 처리가 기존 공통 계약을 복제하면 결함이다. 예외가 필요하면 공통 계약으로 승격할지 다른 의미의 컴포넌트인지 먼저 판정하고 이유를 남긴다.
- 컴포넌트 단위로 검증한다. UX/UI 정본의 상태 계약·상호작용 상태·테마 동등성을 컴포넌트의 실제 렌더에서 대표 폭으로 확인한다. 소비자 화면에서는 컴포넌트가 올바른 상태·이벤트를 주고받는지만 검사한다. 공통 컴포넌트를 바꾸면 사용처를 전수 검색하고 대표 소비자 체인을 다시 실행한다.
- 카탈로그를 코드 가까이에 둔다. 저장소가 story·preview·catalog 패턴을 이미 쓰면 모든 공용 variant와 상태를 그곳에 등록한다. 별도 도구가 없으면 컴포넌트 테스트가 실행 가능한 카탈로그이며, 문서를 위해 새 프레임워크를 도입하지 않는다.

CBD 판정은 "컴포넌트 파일이 있는가"가 아니라 "같은 개념의 구조·상태·행동을 바꾸는 곳이 정확히 하나인가"다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "급하니 복사해서 조금만 고치자" | 두 사본은 곧 다르게 진화하고, 버그는 한쪽에서만 고쳐진다. 차이는 파라미터로 표현한다 |
| "둘이 비슷하니 미리 공통화하자" | 변경 이유가 다르면 공통 코드가 양쪽 조건문으로 부푼다. 추출은 두 번째 실재 반복에서 |
| "이 화면만 살짝 다르게 CSS로 덮자" | 공통 계약 밖의 우회는 다음 변경 때 조용히 깨진다. variant로 올리거나 다른 컴포넌트로 판정한다 |
| "이 숫자는 한 번만 쓴다" | 한 번 쓰는 리터럴도 의미가 이름에 없으면 다음 사람이 다른 값으로 다시 쓴다 |
| "boolean prop 하나만 더 추가하자" | prop 조합이 불가능 상태를 만든다. 의미 있는 variant로 묶는다 |

## 위험 신호

- 복사-붙여넣기 흔적, 같은 상태 목록·상수의 재선언, 흩뿌린 리터럴·매직 문자열 분기
- 화면마다 다르게 보이는 같은 요소, 화면 파일의 raw 공용 제어·하드코딩 색·간격
- boolean prop 누적, 화면별 조건문이 쌓인 공용 컴포넌트, 스타일 전달만 하는 래퍼
- 같은 상태를 컴포넌트·전역·서버가 중복 소유
- 공용 컴포넌트 수정 후 영향받는 화면을 검색 없이는 알 수 없음

## 종료 게이트

- [ ] diff의 리터럴을 전수 확인했고 남은 것마다 이유가 있다
- [ ] 같은 로직·UI·상수의 사본이 없다(중복 검색 실측)
- [ ] 공용 컴포넌트를 바꿨다면 사용처 전수 검색과 대표 소비자 체인 실제 렌더를 확인했다
