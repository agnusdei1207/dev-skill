# 설계: 시스템 아키텍처 · 데이터 모델 · API 계약

이 파일은 시스템 아키텍처, 데이터 모델, API 계약을 소유한다. 새 컴포넌트·서비스·통합·데이터 흐름, 새 저장 데이터·개체, 새 API·엔드포인트·이벤트·공개 인터페이스가 생기면 구현 전에 설계한다. 프로세스 내부의 모듈·폴더·의존 방향은 코드 조직 정본이, 유비쿼터스 언어·바운디드 컨텍스트와 컨텍스트 사이의 교류 규칙은 도메인 모델링 정본이, 스키마의 안전한 진화·마이그레이션은 교차 품질 정본이 소유한다. 되돌리기 어려운 설계 결정(저장소 선택, 공개 계약, 분산 여부)은 인텐트 정본의 결정 절대로 사람이 답한다.

## 시스템 아키텍처

- 단순성 우선. 필요를 충족하는 가장 단순한 아키텍처가 가장 좋다. 기본은 모듈러 모놀리식이다. 분산(서비스 분리·메시지 인프라)은 측정된 실제 필요(독립 배포·독립 확장·장애 격리)가 있을 때만 도입한다.
- 컴포넌트·책임. 컴포넌트·서비스마다 단일 책임과 소유 범위를 식별한다. 함께 바뀌는 것은 한 컴포넌트에, 따로 바뀌는 것은 나눈다. 모든 이유로 바뀌는 거대 컴포넌트를 만들지 않는다.
- 경계·계약. 컴포넌트 사이 경계는 명시적 계약(API·이벤트 스키마)이다. 안정적이고 버전이 관리되며 내부를 숨긴다. 계약 어휘는 용어집을 따르고, 경계 사이의 관계(부패 방지 계층 등)는 도메인 모델링 정본의 컨텍스트 맵으로 정한다.
- 데이터 흐름·진실의 원천. 데이터·제어가 어떻게 흐르는지와 무엇이 진실의 원천인지 정한다. 같은 데이터를 두 컴포넌트가 소유하지 않는다. 공유 가변 상태를 피하고, 공유가 필요하면 소유자를 하나 정해 나머지는 그를 통해 읽는다.
- 동기 vs 비동기. 즉시 응답이 필요하면 동기, 결합을 낮추거나 부하를 평탄화하거나 오래 걸리면 비동기(큐·이벤트). 비동기는 멱등성·순서·중복 처리를 함께 설계한다. 길게 연쇄된 chatty 동기 호출은 지연·결합·장애 전파를 키운다.
- 상태·확장. 무상태 컴포넌트는 수평 확장이 쉽다. 상태가 어디 사는지 정하고, 캐시 계층을 두면 무효화를 함께 설계한다. 확장은 수직을 먼저, 수평은 병목을 측정한 뒤에.
- 배포 토폴로지·장애 도메인. 어떻게 배포·실행되고 장애 도메인이 무엇인지 정한다. 한 컴포넌트가 죽으면 무엇이 저하되고 무엇이 살아 있는지(우아한 저하)를 설계한다. 저장소·구성·비밀의 위치와 경계를 정한다.
- 기술 선택. 런타임·프레임워크·인프라는 적합성과 검증됨으로 고른다. 새로움 때문에 고르지 않는다. 새 기술 하나하나가 운영 부담이다.

## 데이터 모델

데이터는 코드보다 오래 살고 잘못된 모델은 두고두고 재작업을 부른다.

- 접근 패턴이 설계를 정한다. 추상적 정규화 이론이 아니라 실제 읽기·쓰기 패턴(무엇을 어떤 키로 조회하고, 무엇을 함께 쓰며, 무엇이 빈번한가)이 모델을 정한다. 도메인 모델을 따르되 화면이나 특정 쿼리 하나에 종속되게 설계하지 않는다.
- 개체·관계. 개체와 관계(1:1, 1:N, N:M), 카디널리티, 소유 관계를 명시한다. N:M은 조인 개체로 모델링한다. 관계의 상한을 "지금은 하나"로 가정하지 않는다. 도메인상 여럿이 가능한 관계(수신자·소유자·주소·역할·기기)는 처음부터 1:N/N:M으로 두고, 단일 컬럼에 여럿을 구겨 넣지(CSV 문자열·JSON 배열 남용) 않는다. 단일 컬럼을 나중에 관계로 바꾸는 것은 다단계 마이그레이션이다. 한 사실은 한 곳에 산다.
- 키·무결성. 기본 키는 안정적으로, 대리 키와 자연 키의 트레이드오프를 판단한다. 외래 키·참조 무결성은 데이터 계층에서 강제한다. 앱은 우회되지만 DB 제약은 최후의 방어선이다. NOT NULL·CHECK·유일·FK 제약으로 불변식을 스키마에 고정한다.
- 정규화 vs 비정규화. 기본은 정규화다. 비정규화는 측정된 읽기 성능 필요가 있을 때만 의도적으로 하고, 그때 생기는 중복의 동기화 비용을 함께 설계한다.
- 인덱스. 실제 쿼리 패턴에 맞춰 hot 경로 기준으로 둔다. 복합·커버링 인덱스를 쿼리에 맞추되 과도한 인덱스는 쓰기·저장 비용을 늘린다.
- 타입·정밀도. 금액은 float가 아니라 decimal, 시각은 타임존 포함 timestamp, 범주는 enum·참조 테이블. stringly-typed 설계를 금지하고 범위·정밀도·인코딩을 명시한다.
- 저장소 선택. SQL·문서·KV·그래프·시계열 중 접근 패턴·정합성 요구·규모로 고른다. 특별한 이유가 없으면 검증된 관계형이 기본이다. 폴리글랏은 실제 필요가 있을 때만. 새 저장소 기술은 운영 부채다.
- 확장 대비. 파티셔닝·샤딩은 필요할 때만 하되 나중에 나눌 수 있도록 키를 설계해 둔다. 무한히 커지는 테이블(로그·이벤트)은 보존·아카이빙 정책을 함께 설계한다.

## API·계약

- 계약 우선. 구현을 먼저 만들고 계약이 새어 나오게 두지 않는다. 계약을 먼저 정의하고 생산자·소비자가 합의한 뒤 구현한다. 계약은 명시적·기계 검증 가능한 형태(스키마·타입)로 두고 그 스키마가 정본이다.
- 요청·응답 모양. 오퍼레이션마다 입력·출력·에러를 명확한 스키마로 정의한다. 필드는 도메인 어휘로, 타입·필수 여부·범위를 명시한다. 소비자가 필요로 하는 것만 노출하고 내부 구조를 흘리지 않으며 over/under-fetching을 접근 패턴으로 조율한다. 리스트는 페이지네이션(커서 기반 권장)이 기본이고 정렬·필터 계약을 명시한다.
- 수량을 계약에 드러낸다. 여럿일 수 있는 것(수신자·대상·첨부·오류)은 처음부터 배열로 설계한다(이름의 수는 식별자·문구·주석 정본). 단일 필드를 나중에 배열로 바꾸는 것은 깨는 변경이며 소비자 전부를 이전시켜야 한다.
- 에러·상태 계약. 에러는 일급 계약이다. 상태 코드·에러 코드·사람이 읽는 메시지·기계가 읽는 코드를 구분하고 소비자가 분기할 수 있게 안정적으로 정의한다. 성공을 실패처럼, 실패를 성공처럼 표현하지 않으며 부분 성공·비동기 수락(202류)의 의미를 명확히 한다. 스택·쿼리·경로 같은 내부 구조를 에러로 노출하지 않는다.
- 멱등성·안전성. 재시도될 수 있는 쓰기에 멱등 키를 설계해 중복 요청이 중복 효과를 내지 않게 한다. 오퍼레이션의 안전성(safe/idempotent/그 외)을 명시해 소비자가 재시도 가능 여부를 안다.
- 버전·하위호환. 하위호환이 기본이다. 필드 추가는 선택적으로, 제거·의미 변경은 확장 후 수축으로 단계화한다. 깨는 변경이 불가피하면 버전을 나누고 소비자 이전 경로·폐기 일정을 계약에 담는다. 소비자는 모르는 필드를 견디게(tolerant reader) 설계한다.
- 계약 테스트. 생산자·소비자가 계약을 지키는지 계약 테스트로 고정한다. 계약이 바뀌면 그 테스트가 먼저 깨지게 한다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "나중에 커질 테니 처음부터 마이크로서비스로" | 분산은 운영·정합성·디버깅 비용이 막대하다. 측정된 독립 배포·확장·격리 필요가 생길 때 나눈다 |
| "지금은 하나니까 단일 컬럼이면 된다" | 단일 컬럼을 관계로 바꾸는 것은 다단계 마이그레이션이다. 도메인상 여럿이면 처음부터 1:N |
| "검증은 앱에서 하니 DB 제약은 필요 없다" | 앱은 우회된다. 스키마 제약이 최후의 방어선이다 |
| "API는 구현하면서 정하자" | 구현이 새어 나온 계약은 내부 구조를 노출하고 바꿀 때마다 소비자를 깬다. 계약을 먼저 정한다 |
| "필드 이름만 바꾸는 거라 괜찮다" | 이름 변경은 깨는 변경이다. 확장 후 수축으로 단계화한다 |

## 위험 신호

- 필요 없이 기본값처럼 분산, chatty 동기 호출, 장애 격리 부재
- 두 소유자를 가진 공유 가변 데이터, 불분명한 진실의 원천, 수평 확장을 막는 상태 결합
- 새로움으로 고른 기술, 경계 계약 부재, 도메인이 아니라 UI를 옮긴 모델
- 여럿 가능한 관계·값을 단일 컬럼·단일 필드·단수 이름으로 고정
- 키·제약 없이 무결성을 앱에만 의존, stringly-typed, 금액 float
- hot 쿼리 인덱스 누락 또는 과잉 인덱스, 성급한 샤딩, 아카이빙 없는 무한 성장 테이블
- 내부 구조를 그대로 노출한 계약, 페이지네이션 없는 목록, 분기 불가한 에러
- 멱등성 없는 재시도 가능 쓰기, 하위호환을 깨는 무단 변경, 버전·폐기 경로 부재, 계약 테스트 부재

## 종료 게이트

- [ ] 새 컴포넌트·통합·데이터 흐름마다 단일 책임·진실의 원천·장애 시 저하 동작이 정해졌다
- [ ] 새 데이터 모델의 카디널리티·키·제약이 실제 접근 패턴과 도메인 수량에 맞고, 데이터 불변식(유일성·참조·상태 전이)이 제약과 회귀 테스트로 고정됐다
- [ ] 새·변경된 API·이벤트의 스키마가 정본으로 있고, 에러·멱등성·버전 정책이 명시됐고, 계약 테스트가 있다
- [ ] 되돌리기 어려운 설계 결정은 사람의 답이 인텐트에 있다
