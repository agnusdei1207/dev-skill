# 코드 조직 (모듈·폴더·파일)

이 파일은 코드가 어디에 사는가를 소유한다: 관심사 분리, 깊은 모듈과 이음새, 폴더 구조와 성장 단계, 모듈 공개 표면과 의존 방향, 파일 단위와 이름, 테스트·설정·스크립트 배치, 구조 감사와 재배치 절차. 도메인 경계를 정하는 법은 도메인 모델링 정본이, 서비스 분리·배포 토폴로지는 설계 정본이 소유한다. 목표는 처음 온 사람이 기능 이름 하나로 관련 파일을 한곳에서 찾고, 새 파일의 자리가 규칙에서 자명한 상태다.

## 1. 원칙

- 기능·도메인 중심으로 묶는다. 한 기능의 코드가 `controllers/`·`services/`·`models/`·`utils/`에 흩어져 전체를 뒤져야 이해되는 구조를 피한다. 최상위 분할은 기술 계층이 아니라 바운디드 컨텍스트·기능이다.
- 함께 바뀌는 것은 가까이 둔다. 한 변경이 여러 먼 폴더를 건드리면(산탄총 수술) 배치가 틀린 것이다.
- 예측 가능해야 한다. 새 파일의 자리가 규칙에서 자명하고, 같은 종류의 파일은 프로젝트 어디서든 같은 자리·같은 이름 규칙을 따른다.
- 기존 구조를 따른다. 저장소에 이미 일관된 구조가 있으면 그것이 정본이다. 같은 문제에 두 번째 구조 패턴을 도입하지 않는다. 바꿀 가치가 있으면 별도 리팩터 인텐트로 전체를 옮긴다. 이미 명료하고 잘 나뉜 구조·이름은 보존하며, 재구성 자체를 목적으로 삼지 않는다.
- 구조는 필요가 만든다. 빈 계층·미래용 폴더·파일 하나짜리 폴더 사슬을 만들지 않는다. 구조는 실제 파일이 생길 때 생긴다.

## 2. 관심사 분리

- 도메인 · 애플리케이션(유스케이스) · 인프라(영속·외부 IO) · 인터페이스(API·UI·CLI)의 책임을 분리한다. 한 함수가 검증·계산·저장·렌더를 다 하면 쪼갠다.
- 하위 계층의 세부(SQL·HTTP 상태·파일 경로·ORM 타입)가 상위 시그니처로 새면 경계를 다시 긋는다.
- 분리는 규칙의 양에 비례한다(도메인 모델링 정본의 적용 강도). 계층은 섞여서 아픈 지점이 생길 때 나눈다.

## 3. 깊은 모듈과 이음새

- 깊은 모듈: 작은 인터페이스 뒤에 많은 구현. 호출자는 소수의 메서드만 배우고 강력한 기능을 얻고(레버리지), 유지보수자는 변경·버그·검증이 한곳에 모여 있다(국소성). 인터페이스란 시그니처만이 아니라 호출자가 알아야 할 모든 것(불변식·순서·에러·성능)이다.
- 얕은 모듈을 배제한다. 인터페이스 복잡도가 구현과 맞먹는 것(패스스루 래퍼, 무의미한 getter/setter, 1:1 전달 계층)은 학습 비용만 있고 레버리지가 없는 부채다.
- 삭제 테스트. 그 모듈을 지운다고 상상한다. 복잡도가 사라지면 패스스루였고, N개 호출자로 다시 나타나면 제 몫을 하던 것이다.
- 이음새(seam)는 코드를 편집하지 않고 행위를 바꾸거나 관측할 수 있는 경계다. 어디에 이음새를 둘지는 그 뒤에 무엇을 둘지와 별개의 설계 결정이다. 테스트와 의존성 주입은 이음새에서만 일어난다. 인터페이스를 지나쳐 안을 테스트하고 싶다면 모듈 모양이 틀린 것이다.
- 어댑터 하나면 가설의 이음새, 둘이면 진짜 이음새. 실제로 변하는 것(운영 + 테스트, 두 provider)이 없으면 이음새를 만들지 않는다. 단, 구현이 하나여도 외부 IO 대체·테스트 격리·호환성 경계를 담당하는 인터페이스는 유지한다. 소비자·현재 책임이 없는 미래용 확장점과 플래그는 제거한다.

## 4. 폴더 구조

### 성장 단계

구조는 코드 양과 경계 신호에 맞춰 한 단계씩 키운다. 단계를 건너뛰어 미리 깔지 않는다.

| 단계 | 모양 | 다음 단계로 올리는 신호 |
|---|---|---|
| 1. 파일 | 기능 하나가 파일 하나 | 파일 안에 서로 다른 변경 이유가 둘 이상, 관련 파일이 생김 |
| 2. 기능 폴더 | `<feature>/` 아래 관련 파일 몇 개 | 도메인 규칙과 IO가 섞여 테스트가 어려움, 파일이 많아 역할 구분이 필요 |
| 3. 컨텍스트 + 계층 | `<context>/domain`·`application`·`infrastructure`·`interface` | 독립 배포·독립 버전·외부 소비자가 생김 |
| 4. 패키지 | 워크스페이스의 별도 패키지 | (분산은 설계 정본의 판정을 따른다) |

### 모듈러 모놀리식 기본형

컨텍스트가 여럿이고 규칙이 있는 백엔드의 기본 모양이다. 언어·프레임워크 관례가 다르면 같은 의미를 그 관례로 옮긴다. 필요 없는 칸은 만들지 않는다.

```text
src/
  <context>/              바운디드 컨텍스트 = 최상위 모듈
    domain/               엔티티·값 객체·불변식·도메인 이벤트. IO 없음
    application/          유스케이스. 로딩→도메인 호출→저장→발행
    infrastructure/       어댑터: DB·외부 API·메시징 구현
    interface/            진입점: HTTP 핸들러·UI·CLI·이벤트 구독
    index                 공개 표면 (이 컨텍스트가 밖에 내주는 것만)
  shared/                 둘 이상의 컨텍스트가 실제로 쓰는 것만 (공유 커널·범용 값 객체)
  app/                    조립 지점: 설정 로딩·의존성 연결·서버 시작
tests/                    컨텍스트를 가로지르는 통합·E2E (단위 테스트는 대상 옆)
```

### 프런트엔드 기본형

```text
src/
  app/ 또는 routes/        라우트·페이지. 배치와 데이터 연결만
  features/<feature>/     기능별 컴포넌트·상태·API 호출·테스트
  components/             둘 이상의 기능이 쓰는 공유 UI (정본 컴포넌트)
  lib/<concern>/          둘 이상의 기능이 쓰는 비UI 로직 (의미 있는 이름으로)
  styles/ 또는 tokens/     디자인 토큰
```

공유 컴포넌트와 토큰의 소유 규칙은 컴포넌트와 재사용 정본이 소유한다.

## 5. 모듈 공개 표면과 의존 방향

- 모듈마다 공개 진입점이 하나다(`index.ts`·`mod.rs`·`__init__.py`·패키지 export). 밖에서는 진입점만 import하고 내부 경로로 깊이 들어가지 않는다.
- 진입점은 공개할 것만 내보낸다. 내부 전부를 재수출하는 barrel은 캡슐화를 없애고 순환 import·번들 비대를 만든다. 공개 표면이 커지면 모듈이 얕다는 신호다.
- 의존은 한 방향으로 흐른다. `interface → application → domain`, `infrastructure → domain`(도메인이 정의한 포트를 구현), `app`은 전부를 조립한다. 도메인은 아무것도 의존하지 않는다. 특화가 일반에 의존하고, 순환은 만들지 않는다.
- 컨텍스트 사이의 교류 규칙은 도메인 모델링 정본의 바운디드 컨텍스트 절에 있다. 폴더로는 다른 컨텍스트의 `domain/`·`infrastructure/`를 직접 import하지 않는 것으로 드러난다.
- 규칙은 도구로 고정한다. 저장소에 의존 규칙 도구(import 경계 린터, 아키텍처 테스트, 워크스페이스 의존 선언)가 있으면 새 경계를 그 규칙에 등록한다. 없으면 import 그래프 grep을 게이트 대신 실측하고, 반복되면 도구 도입을 제안한다.

## 6. 파일 단위

- 파일 하나 = 한 개념 또는 한 변경 이유. 파일 이름이 그 내용을 정직하게 요약해야 한다.
- 쪼개는 신호: 파일 안에 서로 다른 변경 이유가 공존, 이름에 "그리고"가 필요, 관련 없는 export가 섞임, 일부만 import하려고 전체를 끌고 옴, 스크롤로 위치를 찾아야 함. 줄 수는 점검 신호일 뿐 규칙이 아니다.
- 쪼개지 않는 신호: 항상 함께 바뀌는 작은 조각들, 한 곳에서만 쓰는 보조 함수, 파일 하나짜리 폴더를 만들게 되는 분할. 함수 하나당 파일 하나 같은 기계적 분할은 탐색 비용만 늘린다.
- 테스트·스토리·스타일처럼 대상에 딸린 파일은 대상 옆에 같은 기본 이름으로 둔다(`order.ts`·`order.test.ts`). 저장소가 별도 트리 관례를 쓰면 그 관례를 따르되 경로는 원본 구조를 그대로 미러링한다.

## 7. 이름

폴더와 파일 이름도 유비쿼터스 언어의 표면이다(도메인 모델링 정본).

- 용어집의 단어로 짓는다. 폴더명·파일명이 용어집과 코드 식별자와 같은 개념을 같은 단어로 부른다.
- 케이싱 규칙은 저장소 전체에 하나다(언어 관례: `kebab-case`·`snake_case`·`PascalCase` 컴포넌트 등). 한 저장소에서 섞지 않는다. 단수·복수 폴더명 규칙도 하나로 정한다.
- 역할 접미사(`.service`·`.repository`·`.test`·`.spec`)는 저장소 관례가 있을 때만, 있으면 예외 없이 쓴다.
- 금지 이름: `utils`·`helpers`·`common`·`misc`·`core`·`manager`·`stuff`·`base`(의미 없는 통칭), `new`·`old`·`v2`·`final`·`tmp`·`copy`(버전·상태를 이름에 박음). 버전은 Git이 소유한다.
- 경로가 이미 말한 것을 이름에서 반복하지 않는다. `order/order-service.ts`보다 `order/service.ts` 또는 관례상 필요한 만큼만. 반대로 이름만으로 찾아야 하는 생태계(같은 이름 파일이 탭에 여러 개 뜨는 관례)라면 저장소 관례를 따른다.

### 공용 코드의 자리

- 공용 코드는 소비자가 닿는 가장 낮은 공통 레벨에 둔다. 두 형제가 쓰면 공통 부모에, 여러 컨텍스트가 쓰면 `shared/`에. 한 모듈만 쓰는 것을 전역으로 올리지 않는다. 소비자 집합이 배치 레벨을 정한다.
- `shared/`·`lib/` 아래도 의미 있는 이름의 모듈로 나눈다(`shared/money`, `shared/time`, `lib/http-client`). `utils.ts` 하나에 무관한 함수를 쌓지 않는다.
- 소비자가 하나로 줄어든 공용 코드는 그 소비자 옆으로 내려보낸다.

## 8. 코드 밖의 파일

- 루트에는 진입 문서(README·운영 계약), 매니페스트·락파일, 툴체인 고정, 저장소 전역 설정만 둔다. 루트에 스크립트·임시 파일·출력물을 쌓지 않는다.
- 스크립트는 `scripts/`에 목적을 말하는 이름으로 둔다(`seed-local-db`, `check-licenses`). 일회성 분석 스크립트는 저장소가 아니라 스크래치에 둔다.
- 생성물·빌드 산출물은 소스와 분리된 경로에 두고 `.gitignore`에 넣는다. 생성 코드를 커밋해야 하는 저장소라면 생성 원본과 명령을 같은 위치에서 알 수 있게 한다.
- 설정 파일은 도구가 요구하는 위치에 둔다. 같은 도구의 설정을 두 형식으로 두지 않는다.
- 사람용 문서는 `docs/`에, 구조는 인텐트 정본이 소유한다. 코드 폴더 안에 설명용 README를 흩뿌리지 않는다. 모듈의 공개 계약 설명이 필요하면 진입점의 문서 주석에 둔다.
- 픽스처·샘플 데이터는 그것을 쓰는 테스트 가까이 두고, 실제 개인정보·비밀을 담지 않는다.

## 9. 구조 감사와 재배치

### 감사 절차

구조 정리를 요청받았거나, 주기 아키텍처 리뷰(리팩터링과 코드 품질 정본)에서, 또는 새 기능의 자리가 자명하지 않을 때 밟는다.

1. 전수 열거한다. 디렉터리 트리와 파일 목록을 생성물 제외로 뽑는다. 눈에 띈 폴더만 보지 않는다.
2. 판정 기준을 먼저 정한다. 아래 표를 기준으로 각 파일·폴더를 같은 잣대로 판정한다.
3. 소비자를 확인한다. 이동·삭제 후보마다 import·참조·빌드 설정·문서 링크를 전수 검색한다.
4. 후보를 묶는다. 컨텍스트 하나·기능 하나 단위로 재배치 증분을 나눈다. 저장소 전체를 한 번에 옮기지 않는다.

| 발견 | 판정 | 조치 |
|---|---|---|
| 빈 폴더, `.gitkeep`만 있는 미래용 폴더 | 불필요 | 제거 |
| 파일 하나짜리 폴더의 사슬(`a/b/c/x.ts`) | 과잉 계층 | 평탄화 |
| 어떤 것도 import하지 않는 파일 | 고아 후보 | 진행 중 작업인지 확인 후 제거 |
| 같은 내용·역할의 파일 둘 | 중복 | 정본 하나로 합치고 소비자 이전 |
| 소비자가 하나뿐인 `shared/` 항목 | 잘못된 레벨 | 소비자 옆으로 이동 |
| 한 기능이 여러 기술 계층 폴더에 흩어짐 | 응집 부족 | 기능 폴더로 모음 |
| 통칭 이름(`utils`·`misc`·`common`) | 숨은 분류 | 의미 단위로 나누고 이름 변경 |
| 순환 import, 하위→상위 의존 | 방향 위반 | 경계 재설정, 포트 도입 |
| 다른 케이싱·접미사 규칙이 섞임 | 관례 분열 | 저장소 규칙 하나로 통일 |
| 루트의 스크립트·임시물·출력물 | 위생 위반 | `scripts/`·스크래치·`.gitignore` |

### 재배치 절차

1. 기준선을 실측한다. 이동 전 게이트(빌드·테스트·린트)를 돌려 green을 확인한다.
2. 순수 이동만 한다. 이동 커밋에는 경로 변경과 그에 따른 import 수정만 넣는다. 동작 변경·이름 변경·정리를 섞지 않는다(리뷰어가 이동과 변경을 구분할 수 있어야 한다). 이력 보존이 되는 이동 명령(`git mv`)을 쓴다.
3. 모든 참조를 같은 변경에서 갱신한다. import·빌드 설정·경로 별칭·테스트 설정·문서 링크·스크립트 경로·CI 설정까지.
4. 흔적을 남기지 않는다. 옛 경로의 재수출 별칭·리다이렉트 파일·호환 스텁을 두지 않는다(공개 패키지의 외부 소비자 호환이 필요하면 그 기간과 제거 시점을 인텐트에 적는다). 빈 디렉터리를 지우고 빌드가 깨지지 않는지 확인한다.
5. 게이트를 다시 돈다. 기준선과 같은 게이트가 green이어야 한다.
6. 구조 지도(`docs/ARCHITECTURE.md`)를 같은 변경에서 갱신한다.
7. 이름 변경은 이동과 별도 증분으로 한다. 용어집을 먼저 고치고 전 표면을 맞춘다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "나중에 커질 테니 계층 폴더를 미리 만들자" | 빈 계층은 예측을 돕지 않고 탐색 비용만 늘린다. 신호가 올 때 한 단계 올린다 |
| "일단 utils에 넣어 두자" | utils는 분류를 미룬 것이다. 소비자 옆에 두거나 의미 있는 이름의 모듈을 만든다 |
| "옮기는 김에 이름도 고치고 정리도 하자" | 이동과 변경이 섞이면 리뷰도 되돌리기도 불가능해진다. 순수 이동 먼저, 변경은 별도 증분 |
| "옛 경로 별칭을 남기면 안전하다" | 같은 것을 두 경로로 찾게 되고 별칭은 영원히 남는다. 참조를 전부 갱신하는 것이 안전이다 |
| "계층별 폴더(controllers/services)가 표준이다" | 기능 하나를 이해하려면 모든 계층 폴더를 뒤져야 한다. 계층은 기능 안에 둔다 |
| "파일이 길어서 쪼갰다" | 줄 수가 아니라 변경 이유가 단위다. 함께 바뀌는 것을 쪼개면 한 변경이 여러 파일로 번진다 |
| "기존 구조가 별로라 새 기능은 새 방식으로 하자" | 두 방식이 공존하면 그 자체가 정합성 결함이다. 바꾸려면 전체를 옮기는 리팩터 인텐트로 한다 |

## 위험 신호

- 새 파일의 자리를 정하는 데 고민이 필요함(규칙이 자명하지 않음)
- 기능 하나 변경이 서로 먼 폴더 서너 곳을 건드림
- `utils`·`common`·`misc`·`helpers` 폴더·파일, `v2`·`old`·`new`·`final` 이름
- 빈 폴더, 파일 하나짜리 폴더 사슬, 루트에 쌓인 스크립트·출력물
- 다른 모듈 내부 경로로의 깊은 import, 전부를 재수출하는 barrel
- 순환 import, 도메인 코드의 프레임워크·DB import
- 한 저장소에 두 구조 패턴·두 케이싱 규칙 공존
- 이동과 동작 변경이 한 커밋에 섞임, 옛 경로 별칭·스텁 잔존

## 종료 게이트

- [ ] 새로 만든·옮긴 파일의 자리가 저장소 구조 규칙에서 자명하고, 이름이 용어집·케이싱 규칙과 일치한다
- [ ] 빈 폴더·고아 파일·중복 파일·통칭 이름을 새로 만들지 않았다(구조 감사 표 해당 항목 0건)
- [ ] 모듈 밖에서 공개 진입점만 import하고, 순환·역방향 의존이 없다(도구 또는 import grep 실측)
- [ ] 재배치는 순수 이동 증분이었고, 모든 참조가 갱신됐고, 별칭·스텁이 없고, 기준선과 같은 게이트가 green이다
- [ ] 구조가 바뀌었다면 구조 지도가 같은 변경에서 갱신됐다
