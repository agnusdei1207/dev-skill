# 플럼빙과 정합성 (위상 4)

"국소 수정을 했는데 실제로는 무엇이 새고 무엇이 낡았는가"를 잡는 위상이다. 배선 전수 추적, 행위 수명주기 경계, 쓰기-정리 비용, 전역 동기화, 데드코드·임시물 제거를 소유한다. 선택 단계가 아니라 모든 작업의 기본이다.

## 절차

1. 이번 변경이 만들거나 바꾸거나 지운 값·이벤트·상태·자원을 열거한다.
2. 각각의 생산자 → 버퍼 → 소비자 → 종료를 검색으로 추적한다.
3. 상태·비동기·영속이 있으면 행위 수명주기 경계 표의 질문에 답한다.
4. 추적 결과로 동기화 반경을 정하고, 반경 안의 상수·메타데이터·계약·테스트·문서를 맞춘다.
5. 데드코드·잔여물을 제거하고, 삭제가 빌드를 깨지 않는지 실제 빌드로 확인한다.

## 배선 전수 추적 (Producer → Buffer → Consumer)

코드를 바꾸거나 제거할 때 영향받는 데이터의 배선을 끝에서 끝까지 추적한다. 생산자(값·이벤트·상태가 처음 생기는 곳) → 중간 버퍼(저장·변환·대기, 상태 전이·순서·용량 한계) → 소비자(최종적으로 누가, 몇 명이 읽는가).

- 추가: 새 생산자를 만들면 읽어야 할 모든 소비자를 같은 변경에서 연결한다. 소비자 없는 생산자는 죽은 배선이다.
- 제거: 소비자를 지우면 그 생산자·버퍼가 여전히 필요한지 확인한다. 생산자 없는 소비자는 빈손을 참으로 오독한다.
- 이동: 옛 위치와 새 위치의 호출부를 모두 갱신한다. 라인 수 감소만으로 리팩터가 안전하다고 판단하지 않는다.
- 무손실: 버퍼 상태 전이, 모달 격리·복원, 인터럽트, 경합, 제어문자 오프셋 불일치 같은 엣지에서 원본 데이터가 유실·변형되지 않는지 확인하고, 확인한 불변식은 회귀 테스트로 고정한다.
- 수량: fan-out, 수신자 여럿(브로드캐스트·멀티캐스트), 결과 여럿일 때 어느 구간도 "하나"를 가정해 첫·마지막 원소만 처리하거나 덮어쓰지 않는지 확인한다. 단수 이름·단일 필드·단일 슬롯 버퍼가 그 가정의 흔적이다. 0개 경로도 같은 변경에서 확인한다.
- 종료·정리 수명주기 (Start → Execute → Finally/Teardown): 배선 추적은 데이터 전달에서 끝나지 않는다. 작업·프로세스·컨테이너의 시작부터 자원 해제·사후 정리까지 추적한다. 정상 성공뿐 아니라 실패, 타임아웃, 외부 인터럽트(SIGINT/SIGTERM), 처리 가능한 종료에서는 finally·종료 훅으로 소유 자원을 회수한다. 강제 종료·호스트 장애로 정리 코드가 실행되지 않으면 소유자 식별과 재시작 시 정리·TTL·reaper 중 환경에 맞는 복구 경로를 검증한다. "취소 시그널 때만 정리"하는 반쪽짜리 조건부 정리는 자원 고갈과 다음 실행 실패를 부르는 배선 결함이다.

## 행위 수명주기 경계 감사

배선은 값이 한 번 이동하는 선이 아니라 요청 하나가 끝날 때까지 이어지는 상태 전이다. 아래 경계를 같은 행위의 한 묶음으로 추적한다.

| 경계 | 반드시 답할 질문 |
|---|---|
| 입력 | raw framing, decode된 payload, 인자, 토큰·바이트 추정에 각각 상한이 있는가. 거부가 부작용보다 먼저인가. |
| 상태 관측 | payload와 revision·read 상태를 한 snapshot으로 읽는가. 남아 있는 상태를 새 activity로 오인하지 않고 revision을 한 번만 소비하는가. |
| 내구성 인계 | `persist → publish/deliver → integrate → ACK` 순서인가. ACK 뒤 데이터가 안전한 축약·삭제 전까지 재시작 가능한 정본에 남는가. enqueue와 replay가 같은 검증을 거치는가. |
| 원자 그룹 | 한 요청의 부작용·도구 결과·최종 결과가 같은 그룹인가. 부분 그룹이 축약·재시도·완료 판정에서 떨어져 나가지 않는가. 완료 신호가 한 경로에서만 발생하는가. |
| 비동기 수명 | task를 외부에 보이기 전에 owner가 등록되는가. sender·handle 사본이 종료를 붙잡지 않는가. 취소·shutdown이 하나의 deadline 안에서 task·permit·projection을 모두 회수하는가. |
| 정본과 투영 | canonical state의 writer는 하나인가. 파생 projection은 별도 경로에서 최신화되고, 초기화 실패 시 먼저 만든 투영과 예약 자원이 rollback되는가. |
| 저장 참조 | content-addressed 이름이 존재한다는 이유만으로 신뢰하지 않고, 재사용 전에 실제 bytes의 digest·length를 다시 확인하는가. |
| 소비자 노이즈 | wake/wait 결과는 준비 사실만 알리고 payload는 하나의 canonical queue에서만 읽는가. 화면 tail·요약·로그가 원문을 중복 소유하거나 정본을 잘라내지 않는가. |

다중 단계 wait·retry·shutdown은 단계마다 새 timeout을 주지 않고 행위 전체의 절대 deadline을 공유한다. "상한이 있다"로 끝내지 않고 transport framing, decode된 값, 도구 인자, 메모리 queue, 결과, 화면 투영 중 어디에 걸리는지를 확인하고, 부작용 전에 거부됨을 증명한다. 텍스트 크기 추정과 분할은 ASCII뿐 아니라 다국어·binary-shaped 입력에서도 같은 정본 함수를 쓴다. 이 경계를 통째로 반증하는 테스트의 모양은 TDD와 구현 정본이 소유한다.

한 경계의 결함을 고쳤으면 같은 primitive를 쓰는 인접 경로를 검색한다. 공백을 찾았다는 이유로 저장소·framework·추상화를 늘리지 말고, 기존 소유 경계에 가장 작은 불변식과 회귀 테스트를 추가한다.

## 쓰기-정리 비용 (Write → Cleanup Cost)

쓰기(생성·수정·삭제)에는 정리·동기화 비용이 따르고, 그 비용을 끝까지 책임진다.

갱신 순서: 정본 먼저, 코드가 따라온다. 변경의 정본(계약·스키마·용어집)부터 정합하게 고치고, 코드·테스트가 그것을 따라 바뀌며, 마지막에 정렬·안정성 체크(위상 4~5)로 닫는다. 코드만 먼저 고치고 문서를 "나중에"로 미루면 낡은 문서가 다음 사람에게 반대 지시가 된다. 정본이 코드 자체인 사실(예: 테스트가 소유한 목록)은 그 코드가 먼저다.

"전역"의 반경은 배선 추적이 정한다. 전역 정합성의 전역은 저장소 전부가 아니라 이 변경이 파급되는 그래프 전체다. 파급이 모듈 안에서 끝남을 추적으로 보였으면 그 안에서 전수하고 밖으로 확대하지 않으며, 공유 계약·상수를 건드렸으면 그 소비자 전부로 넓힌다. 좁히는 근거도 넓히는 근거도 추적이지 추측이 아니다. 반경 밖 정렬은 낭비이자 diff 오염이고, 반경 내 누락은 정합성 위반이다.

반경 내 동기화 대상:

- 상수·기본값: 여러 모듈·패키지가 공유하는 상수(기본 한도·용량·토큰 수)를 한 곳만 바꾸고 나머지를 방치하지 않는다.
- 패키지 메타데이터 및 인프라 플럼빙: 매니페스트·락파일의 버전·이름·설명뿐 아니라 빌드 래퍼·런타임 이미지·실행 격리 스크립트·배포 번들 간의 리소스 상한·도구 버전·환경변수 바인딩까지 1:1로 동기화한다. 파일 목록은 저장소 운영 계약이 정한다.
- 명세·스키마·계약: 에이전트 명세, 스키마 파일, 타입 정의, API 계약.
- 테스트 동반 갱신: 코드가 바뀌면 그것을 검증하는 테스트도 100% 함께 바뀐다. 낡은 테스트가 옛 동작을 계속 통과시키거나 새 동작에 대응하는 테스트가 없으면 정합성 위반이다.
- 문서·도움말·라벨: 인텐트의 AI 판정 절, 용어집, README, API 문서, 도움말 텍스트, 명령 목록, UI 라벨을 실제 동작과 맞춘다. 프롬프트·도구 설명 텍스트를 바꾸면 그것을 검증하는 스냅샷·테스트가 낡을 수 있으니 함께 갱신한다.
- 단일 정본: 같은 사실을 두 곳에 적으면 하나만 갱신되어 반대 지시가 된다. 검사 대상 목록·숫자는 테스트나 스키마가 소유하고 문서는 복제하지 않는다.

## 데드코드·잔여물 제거

같은 변경에서 하나도 남기지 않는다.

- 미사용 import·함수·상수·필드, 도달 불가 분기, `dead_code` 경고 대상.
- 소비자가 사라진 생산자, 생산자가 사라진 소비자, 오지 않을 값을 기다리는 대기 코드.
- 낡은 레거시 함수·호환 스텁·별칭 사본 및 구 프로젝트 식별자(이전 패키지명, 옛 환경변수 접두사, 사문화된 CLI 옵션). 전역 검색으로 잔여물을 완전히 박멸한다(단, 저널 역호환 직렬화 마커 등 인텐트에 기록된 명시적 호환 레이어는 예외).
- 분석용 스크립트, 스크래치 파일, 디버그 로그·`print`·`dbg!`, 주석 처리한 옛 코드, 이유 없는 `TODO`, 임시 브랜치·워크트리. 남길 TODO는 이유와 함께.
- 커밋 대상이 아닌 생성·빌드 산출물은 `.gitignore` 경계 안에 둔다. 파일을 지운 뒤 빈 디렉터리가 빌드(Docker `COPY` 등)를 깨지 않는지 실제 빌드로 확인한다.
- `.env`·자격증명·인증서·키·토큰·운영 엔드포인트를 정리 중에도 출력·커밋·스테이징하지 않는다.

## 공개 경계 (해당 시)

공개 저장소·산출물을 다루면 공개해도 되는 경로만 명시적으로 스테이징하고, 도너·비공개 배포 자료·인증서·kubeconfig 같은 파일이 포함되지 않았음을 내용을 출력하지 않고 확인한다. 방법론·전략·내부 경로를 공개 저장소에 파일로도 커밋 메시지로도 남기지 않는다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "필드 하나 추가한 것뿐이다" | 읽어야 할 소비자가 연결되지 않으면 죽은 배선이다. 추가와 연결은 같은 변경이다 |
| "취소될 때만 정리하면 된다" | 실패·타임아웃·인터럽트 경로의 미해제는 다음 실행을 깨는 자원 고갈이 된다 |
| "문서는 나중에 맞춘다" | 낡은 문서는 다음 사람에게 반대 지시가 된다. 정본 먼저, 코드가 따라온다 |
| "혹시 모르니 옛 함수는 남겨 두자" | 소비자 없는 코드는 거짓 신호다. 명시적 호환 계약이 없으면 지운다 |
| "전역 정합이니 저장소 전체를 정렬하자" | 반경은 추적이 정한다. 반경 밖 정렬은 낭비이자 diff 오염이다 |

## 위험 신호

- 소비자 없는 생산자, 생산자 없는 소비자, 오지 않을 값을 기다리는 대기 코드
- 성공 경로에서만 해제되는 자원, 단계마다 새로 주어지는 timeout
- 한 곳만 바뀐 공유 상수·버전·리소스 상한
- 코드와 함께 바뀌지 않은 테스트·스키마·문서·도움말
- 미사용 import·디버그 출력·주석 처리 코드·구 식별자 잔존, 빈 디렉터리
- 근거 없이 넓히거나 좁힌 동기화 반경

## 종료 게이트

- [ ] 변경된 값마다 생산자와 모든 소비자를 추적했고 죽은 배선이 없다
- [ ] 상태·비동기·영속이 있다면 수명주기 경계 질문에 답했고, 모든 종료 경로에서 자원이 회수된다
- [ ] 추적이 보인 반경 안의 상수·메타데이터·계약·테스트·문서가 동기화됐다
- [ ] 데드코드·임시물이 남지 않았고, 삭제 후 빌드가 깨지지 않음을 실측했다
