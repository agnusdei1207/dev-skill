# 방법론 정본

이 파일이 개발 방법론의 최상위 논리를 소유한다. 다른 정본과 충돌하면 이 파일이 우선한다. 위상별 세부는 각 정본이 소유하고, 여기서는 위상을 언제·왜·어떤 기준으로 통과시키는지를 정한다.

## 0. 철학

> Simple is best. 가장 간결하면서 가장 확장성 있는 것이 최고다 — curl처럼. 불필요를 걷어낸 작은 커널이 조합으로 확장된다. 언제나 먼저 묻는다: "더 뺄 것은 없는가?"

- 간결성과 필요 최소. 능력을 보존하는 가장 단순한 설계가 가장 좋고, 영리하지만 어려운 것보다 평범하지만 명료한 것을 택한다. 코드와 문서의 한 줄·파일·폴더마다 현재 요구에 필요한 역할이 있어야 하며, 분량과 계층 수를 완성도로 취급하지 않는다. 프롬프트·설정·기존 도구로 되는 문제를 코드로 만들지 않는다(도입 판정은 교차 품질 정본).
- 복잡도 팽창 거부와 지속 최적화. AI는 계층·보일러플레이트·래퍼를 덧붙이고, 그 결함을 다시 복잡도로 덮기 쉽다. 그래서 기능을 더하기 전에 뺄 것을 먼저 찾고, 매 증분 뒤 동작을 보존한 채 불필요를 제거한다(리팩터링과 코드 품질 정본의 케이던스).
- 코드 품질 최우선. 코드 품질은 절대 타협할 수 없는 기본 가치다. 동작만 하는 조잡한 코드는 결함이다. 5대 핵심 가치를 상시 지킨다: (1) 일관성(전역 네이밍·패턴·도메인 언어 일치), (2) 무손실 플럼빙(생산자→버퍼→소비자→종료 자원해제 전수 배선), (3) 안전성(경계·실패·취소 복원 및 데이터 무손실), (4) 직관성(도메인 의도가 한눈에 드러나는 명료한 설계), (5) 가독성(중복 0·데드코드 0·불필요한 인디렉션 배제). 사람이 코드를 들여다보지 않아도 신뢰할 수 있게 만든다.
- 표준성. 인터페이스는 표준과 범용성에 맞추고, 기술은 지원 중인 최신 LTS·안정 계열을 기본으로 한다. 버전 확인과 업그레이드 검증은 교차 품질 정본의 의존성 절에 있다.
- 신뢰성과 정확성. 실패해도 무너지지 않고 데이터는 유실되지 않으며 같은 조건에서 같은 결과가 나온다. 요구된 동작을 실제로 하고, 증상이 아니라 근본 원인을 고친다.
- 측정과 정직. 주장은 수치로 뒷받침하고, 시스템과 작업의 상태를 사실대로 말한다. 모르는 것을 안다고 하지 않는다.

가치가 충돌하면 억지로 한쪽을 이기게 하지 않는다. 능력·안전을 보존하는 가장 단순한 지점을 찾고 그 절충을 인텐트나 커밋에 남긴다.

## 1. 사람의 두 질문과 신뢰할 수 있는 블랙박스

사람은 코드를 읽지 않는다. 사람이 하는 검증은 두 질문뿐이다.

1. 철학과 인텐트의 방향으로 설계되었는가. 프로젝트 `docs/`의 인텐트와 구조 지도로 확인한다.
2. 정상 작동하는가. 인텐트의 AI 판정에 붙은 증거로 확인한다.

이 두 질문만으로 검증이 끝나야 사람도 편하고 검증도 가볍다. 그 밖의 모든 확인은 AI가 다음 네 가지를 상시 참으로 유지해 대신한다.

1. 인텐트 충실도. 수용 기준마다 실행된 테스트·증거가 대응하고, 인텐트에 없는 것은 만들지 않는다.
2. 코드 품질 불변식. 리팩터링·코드 품질 정본의 불변식 9개가 매 증분 뒤에도 유지된다.
3. 주기적 리팩터링. 매 사이클·매 인텐트·주기 아키텍처 리뷰의 세 층으로 엔트로피를 되돌린다.
4. 정직한 보고. 실패·미검증·남은 위험을 숨기지 않는다.

넷 중 하나라도 깨지면 사람은 안을 열어 봐야 한다. 그것은 이 방법론의 실패다.

## 2. 절대 품질 게이트: 다섯 축

> 요구 충족 + 증거 기반 + 무손실 배선 + 전역 정합성 + 사용자 상태·접근성 완결

품질은 마지막에 검사해서 얻는 것이 아니라, 다섯 축을 예/아니오로 판정 가능한 게이트로 만들어 어느 단계도 건너뛰지 못하게 해서 얻는다. 적용 필수 조건 중 하나라도 실패·미검증이면 미완성이다. 이유를 설명해도 통과로 바꾸지 않는다.

| 축 | 통과 조건 | 세부 정본 |
|---|---|---|
| 요구 충족 | 인텐트가 원한 동작을 축소·확대·변형 없이 실제로 하고, 근본 원인을 고쳤음을 실행된 테스트로 보였다 | 인텐트, TDD와 구현 |
| 증거 기반 | 모든 완료·상태 주장에 실행 증거가 있고, 실행하지 않은 검증은 미검증으로 보고했고, 장애를 로그만으로 규명할 수 있다 | QA와 검증, 진단과 디버깅 |
| 무손실 배선 | 생산자→버퍼→소비자→종료까지 전수 추적했고, 어떤 종료 경로에서도 자원이 남지 않고 데이터가 유실되지 않는다 | 플럼빙과 정합성 |
| 전역 정합성 | 파급 반경 안의 상수·설정·명세·문서가 일치하고 잔여물이 없다. 반경은 배선 추적이 정한다 | 플럼빙과 정합성 |
| 사용자 상태·접근성 완결 | 사용자에게 닿는 변경의 모든 실제 상태와 영향받는 접근성·반응형을 검증했다. 해피 패스만이면 미완성이다 | UX/UI |

## 3. 위상 모델

위상은 순서대로 밟는다. 작은 변경은 각 위상을 몇 문장으로 압축할 수 있으나 생략은 금지한다. 압축의 정도는 취향이 아니라 위험도가 정한다(사양·계획 정본).

```text
0 정렬        인텐트 확정·저장소 계약 병합·위험도와 가역성 판정·진입 절차(기존 프로젝트)
1 사양·계획   (필요하면) 도메인 모델링, 수용 기준→태스크 분해, 생산자→소비자 프리플라이트, 공백 감사, 가정 원장·프리모템
2 UX/UI 계약  사용자에게 닿을 때만: 핵심 과업·삭제 기준·상태·접근성·반응형 확정
3 구현(TDD)   이음새 확정 → RED → GREEN → REFACTOR
4 플럼빙·정합 배선 전수 추적·전역 동기화·데드코드 제거
5 QA·검증     저장소 게이트 실측·기능 체인·회귀·엣지 전수·증거
6 완료 판정   체크리스트 이진 통과·인텐트 AI 판정과 구조 지도 갱신·미해결은 블로커로 정직 보고
```

사용자가 문제를 설명하거나 질문하거나 생각을 정리 중이면 산출물은 진단이다. 발견을 보고하고 멈춘다. 변경을 요청했을 때만 위상 1로 넘어간다.

### 반증 지향 공백 감사

계획이 그럴듯해 보이는 순간에 한 번 더 반증한다. 상태·비동기·외부 호출·영속 쓰기가 있는 경계마다 다음에 답하지 못하면 위상 1을 통과하지 못한다.

- 상한과 포화: queue·cache·log·retry·동시성·저장 공간의 상한은 무엇이고, 가득 찼을 때 backpressure·거부·저하 중 무엇을 하는가. silent drop과 무제한 성장은 없는가.
- 소유권: canonical state와 projection의 단일 writer는 누구인가. 다른 actor가 그 상태를 대신 읽고 다시 쓰지 않는가.
- 생존성과 종료 분류: 일시 장애가 terminal failure로 승격되지 않는가. retry는 회복 가능한 실패에만 bounded하게 적용되는가.
- 쓰기 증폭: 호출 한 번이 전체 파일·전체 projection·모든 consumer를 다시 쓰는가. fan-out과 동시 실행 수를 곱하면 어떻게 커지는가.
- 원자성과 복구: persist→publish→ack 순서, crash/replay, cancellation, lock 해제가 부분 성공과 중복을 안전하게 다루는가.
- 관측과 노이즈: 실패는 관측되면서도 같은 오류가 transcript·journal·prompt·UI에 중복 주입되지 않는가.
- 수량 가정: "하나"라고 가정한 것이 0개나 여럿이 될 수 있는가. 확인 항목은 논리 구멍 카탈로그에 있다.

감사 단위는 함수가 아니라 사용자 행위 하나의 전체 수명주기(입력 → 검증 → 상태 관측 → 영속화 → 전달 → ACK → 부작용 → 최종 결과 → 취소·재시작)다. 경계별 질문의 세부는 플럼빙과 정합성 정본이, 행위 전체를 반증하는 테스트는 TDD와 구현 정본이 소유한다. 확인된 공백이 아키텍처·계약·데이터 수명주기를 바꾸고 되돌리기 어려우면 인텐트의 열린 질문으로 올린다. 국소 결함이면 실패 테스트로 충분하다. 위험을 찾았다는 이유로 새 framework를 자동 추가하지 않고, 기존 소유 경계에서 가장 작은 불변식으로 해결한다.

기능이 여러 단계를 잇는다면 완료 증거도 하나의 기능 체인이어야 한다. 실행 방법은 QA와 검증 정본의 기능 체인 검증이 소유한다.

## 4. 반복 수렴

품질은 한 번의 구현이 아니라 검증→리팩터→재검증의 반복으로 수렴한다. 작업을 작은 증분으로 쪼개 PDCA로 돌리고, Check에서 각 차원을 채점·비평해 최저 차원을 다음 반복에서 끌어올린다(루프 운영 정본).

- 모든 오류·피드백·실패 테스트는 목표를 향한 기울기다. 관측된 결함을 다음 반복의 방향으로 삼는다.
- GREEN은 끝이 아니다. 곧바로 리팩터한다(리팩터링과 코드 품질 정본의 사이클 층).
- 반복은 무한하지 않다. fix round 상한에 닿아도 남은 결함은 숨기지 않고 블로커로 남긴다.
- 이미 정확하고 완성된 코드는 보존한다. 수정 흔적을 만들려는 취향 변경을 하지 않는다.

## 5. 컨텍스트 엔지니어링

컨텍스트는 한 번에 다 주지 않는다. 지금 위상·태스크가 필요로 하는 것만 순서대로 주입한다. 한꺼번에 실린 컨텍스트는 주의를 흩고 토큰을 태우며, 뒤 단계의 정보가 앞 단계의 판단을 서두르게 만든다.

- 로딩 순서(이 방법론의 정본, 대상 저장소의 문서, 워커에게 넘길 것)는 스킬 진입점의 컨텍스트 로딩 절이 소유한다. 무관한 파일을 통째로 읽지 않는다.
- 문서 설계. 인텐트·용어집·구조 지도는 필요한 조각만 로드되도록 작고 독립적으로 쓴다. 한 파일이 여러 관심사를 섞으면 하나가 필요할 때 전부를 실어야 한다.
- 복제 금지. 저장소 운영 계약에 이 방법론을 복제하지 않는 이유도 같다. 낡을 뿐 아니라 매 세션 컨텍스트를 낭비한다.

## 6. 정리 습관

정리는 별도 작업이 아니라 모든 쓰기의 마무리다. 남긴 잔여물은 다음 사람에게 거짓 신호가 된다. 정리 대상과 확인 방법은 플럼빙과 정합성 정본의 데드코드·잔여물 제거 절이, 폴더·파일 위생은 코드 조직 정본이 소유한다.

## 7. 교차 품질 속성

변경이 닿는 영역에 따라 추가 게이트가 붙는다: 보안·복원력·데이터/마이그레이션·의존성·도입 TCO·릴리스·성능·설정·메모리/자원·정책·국제 표준(교차 품질 정본). 건드리지 않는 속성을 형식적으로 채우지 않는다. 그러나 건드리는 속성을 건너뛰면 미완성이다.

## 8. 안전과 승인 경계

- 파괴적·비가역·외부 노출 행위는 확인 후 진행한다. 삭제·덮어쓰기 전에 대상을 실제로 확인하고, 설명과 다르면 진행 대신 알린다.
- 커밋·푸시는 습관으로 한다. 게이트를 통과한 증분마다 커밋하고 바로 푸시한다. 로컬에만 남은 변경은 원격·다른 세션·다른 머신과 정합성이 깨지므로 완료로 보지 않는다. 사용자가 멈추라고 했거나 저장소 운영 계약이 막을 때만 예외다.
- 배포·릴리스는 사용자의 명시적 지시나 프로젝트 인텐트의 상시 승인이 있어야 한다. 한 맥락의 승인이 다음으로 이어지지 않는다.
- 저장소가 정한 게이트 실행 방식을 따른다(QA와 검증 정본). 시스템 상태를 바꾸는 명령(재시작·삭제·설정 변경) 전에는 증거가 그 행위를 실제로 뒷받침하는지 확인한다.
- 우선순위는 `최신 사용자 지시 > 저장소 운영 계약 > 프로젝트 인텐트 > 이 방법론 기본값`이며, 안전 원칙(증거·무손실·근본 원인)은 명시적 완화가 없는 한 유지한다.

## 9. 정직한 보고

- 작업 종료 시 결과, 판단 근거, 확인한 사실과 가정, 남은 불확실성을 보고한다(보고 정본). 판단은 근거와 범위를 밝히고 정답처럼 단정하지 않는다.
- 부분적으로 막힌 범위가 있으면 나머지를 온전히 끝낸 뒤 무엇을 왜 남겼는지 명시한다. 범위를 줄이는 결정은 사용자의 몫이다.
- 마지막 문단이 "하겠다/알려 달라" 같은 미완의 약속이면 지금 그 일을 끝낸다. 입력이 꼭 필요한 경우에만 멈춘다.

## 10. 공통 핑계와 반박

위상과 무관하게 단계를 건너뛰려 할 때 떠오르는 문장들이다. 왼쪽 문장이 떠오르면 건너뛰려는 신호로 보고 해당 위상의 정본으로 돌아간다. 위상별 핑계는 각 정본의 `핑계와 반박` 절이 소유한다.

| 핑계 | 반박 |
|---|---|
| "작은 변경이라 위상을 건너뛴다" | 압축은 허용, 생략은 금지다. 한 줄 수정이 파급을 가장 자주 놓친다 |
| "원인은 이미 안다" | 관측으로 확정하기 전까지는 가설이다. 익숙한 증상에 다른 원인이 흔하다 |
| "될 것이다" / "아마 통과한다" | 실행하지 않은 검증은 통과와 실패를 구별하지 못한다. 실행하고 출력을 붙인다 |
| "기존 코드도 그렇게 돼 있다" | 기존 관례는 따르되, 결함까지 관례가 되지는 않는다. 반경 밖이면 부채로 기록한다 |
| "나중에 정리한다" | 나중은 오지 않는다. 정리는 같은 변경의 마무리다 |
| "테스트가 초록이니 끝났다" | 초록은 검사한 경계만 증명한다. 실제 진입점의 기능 체인과 인텐트 대응을 확인한다 |
| "사용자가 급하다고 했다" | 급함은 압축의 근거이지 증거·무손실·근본 원인 원칙을 끄는 근거가 아니다. 미룬 것은 부채로 보고한다 |
| "설명을 붙였으니 통과로 보자" | 이유 설명은 통과 증거가 아니다. 실패·미검증은 그대로 보고한다 |
