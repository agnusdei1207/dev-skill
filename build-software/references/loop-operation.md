# 루프 운영

이 파일은 자율 실행을 소유한다. 사람이 인텐트를 한 번 주면, 이 루프가 작업을 작은 증분으로 나눠 PDCA로 돌려 완성까지 수렴시킨다. 채점 루브릭, 변경 단위의 모양(diff·커밋), 리뷰의 태도, 병렬 위임 경계, 중단·인계 기준, 커밋 케이던스도 여기가 정본이다.

## 증분 원칙

품질은 한 번에 주입되지 않는다. 작업을 작은 증분으로 쪼개고, 각 증분을 필수 조건 검증까지 완결한 뒤 다음으로 간다. 한 증분은 그 자체로 검증·채점 가능한 최소 변경이다. 큰 덩어리를 미완성 상태로 쌓아 두지 않는다.

## PDCA 사이클

1. Plan: 이 증분의 파일·인터페이스(생산자→소비자)·검증을 사양·계획 정본 형식으로 명시하고, RED 테스트 스텝을 먼저 적는다.
2. Do: TDD와 구현 정본대로 RED→GREEN→REFACTOR를 돌려 최소 구현한다.
3. Check: 적용 필수 조건을 증거로 판정하고 저장소 게이트를 실측한다. 적대적 셀프 리뷰에서 결함을 찾으면 회귀 테스트를 먼저 만든다. 비교가 필요할 때만 보조 점수를 붙인다.
4. Act: 실패·미검증부터 해소한다. 영향받는 이웃 조건도 검증하고 배운 것을 다음 증분의 Plan에 반영한다.
5. 기록: LOW는 결과·증거를 간결하게 보고한다. MED/HIGH는 결정·남은 결함·필요한 보조 점수를 진행 원장에 남기고 다음 증분으로.

## 채점 루브릭

차원은 새 기준이 아니라 방법론 정본의 다섯 축(1~5)과 도메인·구조, 간결성·코드 품질, 설계, 교차 품질(6~9)을 채점 단위로 나눈 것이다. 각 차원을 해당 정본의 위험 신호(교차 품질은 `실패로 본다`)에 대조해 0~100으로 채점한다. 해당하지 않는 차원(화면 없는 변경의 UX 등)은 `N/A`로 게이트에서 제외한다.

| # | 차원 | 정본 | 무엇을 보는가 |
|---|---|---|---|
| 1 | 인텐트 충족 | intent, methodology, diagnosis-and-debugging, tdd-and-implementation, logic-hole-catalog | 수용 기준을 실제로 만족하는가, 원인을 관측으로 확정하고 근본 원인을 고쳤는가, 사소한 가정(수량·경계·시간·문자열·순서·단위)의 구멍이 없는가 |
| 2 | 증거·검증 | qa-and-verification, tdd-and-implementation(테스트 전략) | 게이트를 실측 통과했고 모든 주장에 증거가 있는가, 테스트가 올바른 수준에 결정적으로 놓였는가 |
| 3 | 무손실 배선 | plumbing-and-consistency | 생산자→소비자 전수, 행위 수명주기 경계, 데이터 무손실, 죽은 배선 없음 |
| 4 | 전역 정합성 | plumbing-and-consistency, maintenance-and-brownfield, loop-operation(변경 위생) | 상수·메타·문서·테스트 동반 갱신, 단일 정본, 기존 관례 준수, 한 목적의 diff·커밋 |
| 5 | UI/UX·상태·접근성 | ux-and-ui | 핵심 과업이 하나로 읽히는가, 불필요한 표면이 없는가, 모든 상태·접근성·반응형·정직한 표시·발견성이 완결됐는가 |
| 6 | 도메인·구조·재사용 | domain-modeling, code-organization, components-and-reuse, naming-and-copy | 용어집과 식별자 일치, 불변식 소유자 하나, 이름의 수가 카디널리티와 일치, 관심사 분리·깊은 모듈·한 방향 의존, 파일 자리가 구조 규칙에서 자명, 재고에서 조립·중복 없음, 리터럴이 상수·enum·설정으로 뽑혔는가 |
| 7 | 간결성·코드 품질 | refactoring-and-code-quality, methodology(철학) | 가장 단순한 설계인가, 품질 불변식(중복 0·데드코드 0·최소 코드·조기 추상화 없음)이 유지되는가, 복잡도 예산 안의 도입인가 |
| 8 | 설계·계약 | design | 새 컴포넌트·데이터 모델·API가 생겼을 때 설계 정본의 위험 신호에 걸리는 것이 없는가 (없으면 N/A) |
| 9 | 교차 품질 | cross-cutting-quality | 건드린 영역의 보안·복원력·데이터·의존성·도입·릴리스·성능·설정·자원·정책 게이트와 완화·롤백의 검증 |

완료 판정은 완료 체크리스트 정본을 따른다. 점수는 비교·개선 우선순위를 설명할 때만 붙이고 이진 판정을 뒤집지 않는다. 조건 집합은 시작 시 정하고 새 영향이 발견되면 근거와 함께 갱신한다.

| 보조 점수 | 재현 가능한 판정 |
|---|---|
| 100 | 모든 적용 조건 통과, 독립 리뷰 또는 별도 반증 검증까지 통과 |
| 90 | 모든 적용 조건 통과, 독립 검증은 아직 없음 |
| 70 | 실행한 조건은 통과했으나 일부 필수 조건 미검증 |
| 50 | 필수 조건에 관측된 실패가 있음 |
| 0 | 해당 차원을 평가할 증거가 없음 |
| N/A | 변경과 무관. 제외 근거 기록 |

여러 상태가 섞이면 실패(50), 미검증(70), 통과(90/100) 순으로 판정하며 증거가 전혀 없으면 0이다. 임의의 중간 점수는 쓰지 않는다. 예: 회귀는 통과했지만 필수 취소 경로 미실행이면 70·미완료, 데이터 유실 관측이면 50이다. 점수를 높이려고 실패 조건을 제외하지 않는다.

## Fix round와 수렴 판정

- 완료 정의는 완료 체크리스트에 있다. 평균으로 실패를 상쇄하지 않는다.
- fix round 상한은 저장소·사용자 계약을 따른다(없으면 기본 5회). 한 round는 결함 확인 → 수정 → 영향 검증이다.
- 실패·미검증부터 해소한다. 통과한 차원을 100점으로 올리려 불필요한 변경·검사를 추가하지 않는다.
- 상한에 남은 결함은 증거·영향과 함께 블로커로 보고한다. 그 결함에 의존하지 않는 작업은 계속한다.
- HIGH 변경은 다른 검토자의 수용 기준·diff·실행 증거 대조 또는 작성 때와 다른 반증 시나리오를 수행한다. 자기 채점을 독립 리뷰라고 부르지 않는다.

## 진행 원장

LOW 변경은 별도 원장을 만들지 않는다. MED/HIGH 원장은 스크래치에 두고 커밋하지 않는다. 종료·인계 전 현재 상태·결정·증거 위치·다음 작업을 인텐트의 AI 판정 절에 옮긴다. 스크래치 보존을 가정하지 않는다.

```text
# 진행 원장 — 인텐트: <번호·제목>
## 프리플라이트
Ruling: <결정> — 이유 — cost if wrong: <틀렸을 때 비용>
| 태스크 | 생산자→소비자 / 공유 자원 | 판정 |
## 태스크 N
- 상태: fix round k/5 진행 | 완료(커밋 범위, review clean)
- 채점표 / 결정 / 남은 Important 결함(다음 태스크 차단 여부)
```

Ruling을 남긴다. 판단이 갈리는 지점(worktree vs main, 도너 취급, 정적 출력 정책 등)마다 무엇을 왜 정했고 틀리면 비용이 무엇인지 한 줄로 적는다. 사람이 알아야 할 Ruling은 인텐트의 `결정`으로 올린다.

## 변경 위생 (diff·커밋·설명)

- 한 변경 = 한 목적. 기능·리팩터·포맷·의존성 갱신을 한 diff에 섞지 않는다. 섞이면 리뷰어가 동작 변경과 이동을 구분하지 못하고 되돌릴 때 함께 사라진다. 리팩터는 별도 증분으로 먼저(또는 뒤에) 낸다.
- 반경 안의 변경만. 지나가다 본 무관한 정리·취향 변경을 끼워 넣지 않는다. 반경 밖 부채는 기록하고 별도 인텐트로 제안한다.
- 리뷰 가능한 크기. 큰 변경은 증분 순서(계약 노출 → 구현 → 소비자 전환 → 옛 경로 제거)로 나눈다. 자동 생성 파일·일괄 포맷은 분리한다.
- 커밋은 원자적이다. 하나의 응집된 변경, 게이트 통과 상태, 단독 되돌리기 가능. 메시지는 무엇을 왜를 담는다. 제목은 결과 한 줄, 본문은 이유·트레이드오프·영향 범위·검증 방법. diff에서 읽히는 "어떻게"를 반복하지 않고, 관련 인텐트 번호를 참조한다. 저장소 규약(Conventional Commits 등, 정체성·트레일러 규칙)을 따르고, 없으면 기존 이력의 형식을 따른다.
- 변경 설명(PR)은 보고 정본의 골격을 따른다: 한 줄 결론 → 설계 결정과 근거 → 검증 수치 → 남은 것. 리뷰어가 어디를 어떤 순서로 읽고 특히 봐 달라는 지점(위험·가정·불확실)을 앞에 둔다. 검증하지 못한 것을 숨기지 않는다.

## 리뷰

리뷰는 두 축으로 나눠 보고 섞어 순위 매기지 않는다. 인텐트 축(수용 기준 대비 누락·부분 구현, 인텐트에 없는 동작의 확대, 구현됐지만 틀린 것)과 품질 축(품질 불변식·코드 스멜 기준선·저장소 규약). 규약을 다 지키고 엉뚱한 것을 만들 수도, 인텐트를 정확히 구현하고 규약을 깰 수도 있다. 한 축이 다른 축을 가리지 않게 따로 보고한다.

- 셀프 리뷰(적대적): 제출 전에 리뷰어의 눈으로 diff를 처음부터 다시 읽는다. 순서는 완료 체크리스트 해당 항목 → 배선 추적 → 이름·문구 → 남긴 잔여물 → 커밋 단위.
- 리뷰를 받을 때: 지적은 확인할 가설이지 정답이 아니다. 코드·실행으로 검증한 뒤 수용하거나 근거를 들어 반박한다. 맞으면 같은 원인의 인접 경로까지 찾아 함께 고친다. 지적된 한 줄만 고친 patch는 클래스를 남긴 마감이다. 취향 차이는 결함이 아니며, 저장소 관례가 이기고, 없으면 한쪽으로 정해 Ruling으로 남긴다. 반영 결과는 무엇을 어떻게 검증했는지와 함께 답한다.
- 리뷰를 할 때: 동작·계약·배선·정합성·안전을 먼저, 스타일은 도구에 맡긴다. 지적은 무엇이 왜 문제이고 무엇이 관측될지를 담는다. "이상해 보임"은 리뷰가 아니다. 범위 확대를 요구하지 않고, 차단과 제안을 구분해 표시한다. AI 생성 코드도 같은 기준으로 본다.

## 자율 실행 원칙

- 되돌릴 수 있고 인텐트에서 따라오는 행위는 묻지 않고 진행한다. "할까요?"로 멈추면 루프가 죽는다.
- 막히면 의존하지 않는 일을 먼저 다 하고, 의존하는 부분만 가정을 명시하거나 인텐트의 열린 질문으로 남긴다. 아무것도 못 하고 멈추는 질문은 어떤 가정으로도 진행이 불가능하거나 틀리면 산출물이 무의미할 때만 한다.
- 오류가 나면 재시도·정보 수집을 스스로 한다. 컨텍스트가 길어졌다고 조기 종료하지 않는다.
- 파괴적·외부 노출 행위는 방법론 정본 8절의 승인 경계를 따른다.

## 병렬 실행과 위임 경계

병렬은 속도를 위한 것이지 정합성을 흔들어도 되는 면허가 아니다.

- 나누는 기준은 배선이다. 프리플라이트에서 생산자→소비자 의존이 없는 태스크만 병렬로 보낸다. 앞 태스크의 인터페이스에 의존하는 태스크는 그 인터페이스가 노출된 뒤에 시작한다.
- 파일 소유는 한 워커에 하나. 같은 파일·공유 자원(루트 설정·락파일·스키마·공용 컴포넌트)을 두 워커가 동시에 쓰지 않는다.
- 위임 계약을 적는다. 범위·비범위·보호 구간·인터페이스·검증 명령·보고 형식을 넘긴다. 계약 없는 위임은 범위 충돌과 중복 구현을 만든다.
- 격리와 통합. 워커는 격리된 작업 공간(worktree·브랜치)에서 작업하고, 통합 시점에 배선 추적·전역 정합성·게이트를 통합된 상태에서 다시 돈다. 각 워커의 green이 통합의 green을 보장하지 않는다.
- 워커의 보고를 검증한다. 실행 로그·수치 없는 "완료"는 받아들이지 않고 통합 전에 직접 실측한다.
- 병렬의 비용(토큰·조정·충돌 해소)이 이득보다 크면 순차로 한다. 작은 작업을 병렬로 쪼개는 것은 최소성 위반이다.

## 언제 멈추고 1:1로 인계하는가

이 루프는 80%를 안전하게 만드는 도구이지 100%를 자율로 강행하는 도구가 아니다. 다음이면 멈추고 사람에게 넘긴다.

- Critical/Important 결함이 fix round 상한에서도 남고, 그 해소가 사람의 방향 결정(제품 판단·트레이드오프)을 요구할 때.
- 인텐트 해석이 갈리고 서로 다른 해석이 실질적으로 다른 산출물을 낳을 때.
- 방법론 정본 8절의 승인이 필요한 행위(커밋·푸시·배포·되돌리기 어려운 삭제)가 남았는데 승인이 없을 때.
- 게이트를 환경·권한 때문에 실행할 수 없어 완료를 증거로 증명할 수 없을 때.

멈출 때는 결정거리를 인텐트의 열린 질문으로, 현재 상태를 AI 판정 절에 남기고, 보고 정본의 골격으로 설계 결론 + 검증 수치 + 남은 결정거리를 압축해 넘긴다. 무엇이 80%까지 됐고 남은 20%가 왜 사람의 판단을 요구하는지 분명히 한다.

## 커밋·푸시 승인 경계와 주기적 커밋

- 기본: 승인 경계는 방법론 정본 8절이다. 승인되지 않았으면 인텐트의 AI 판정 절로 추적성만 남긴다.
- 주기적 커밋(승인 시): 사람이 주기적 커밋·푸시를 지시하거나 프로젝트 인텐트가 상시 승인하면 그것을 케이던스로 삼는다. 필수 조건 게이트를 통과한 증분마다 하나의 원자 커밋을 남긴다. 최신성이 유지되고 세션·머신 문제로 작업이 날아갈 위험을 막는다. 미완성·깨진 상태는 커밋하지 않는다.
- 푸시는 원격 백업이자 노출이다. 공개 경계·비밀 유출이 없음을 확인한 뒤 푸시한다.
- 릴리스는 저장소가 정의한 완료 계약(모든 배포 표면의 버전 일치, 검증기 통과)을 만족할 때만 성공으로 보고한다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "한 번에 다 만들고 마지막에 검증하자" | 미완성 덩어리는 결함 위치를 숨긴다. 증분마다 필수 조건까지 완결한다 |
| "평균 점수가 높으니 통과다" | 평균은 실패를 상쇄하지 못한다. 필수 조건 하나라도 실패·미검증이면 미완료다 |
| "할까요?" | 되돌릴 수 있고 인텐트에서 따라오는 일은 묻지 않고 진행한다. 묻는 것은 사람 몫의 결정뿐이다 |
| "워커가 완료라고 했다" | 실행 로그·수치 없는 보고는 받아들이지 않는다. 통합 상태에서 직접 실측한다 |
| "리뷰어 지적이니 그대로 반영한다" | 지적은 확인할 가설이다. 검증 후 수용하고, 같은 원인의 인접 경로까지 고친다 |
| "자기 채점이 독립 리뷰다" | 작성 때와 다른 검토자나 다른 반증 시나리오만 독립 검증이다 |

## 위험 신호

- 증분 없이 통짜 구현, 필수 조건 판정 없는 완료 선언, 증거 없는 점수, 평균으로 통과시킨 게이트
- 상한 도달 결함의 은폐
- 목적이 섞인 diff, "어떻게"만 있는 커밋 메시지, 셀프 리뷰 없는 제출
- 검증 없는 지적 수용이나 근거 없는 거부, 인접 경로 미감사, 두 축을 섞어 순위 매긴 리뷰
- 배선 의존이 있는 태스크의 병렬화, 워커 보고의 무검증 수용
- 승인 없는 커밋·푸시, 원장·계획의 저장소 커밋
