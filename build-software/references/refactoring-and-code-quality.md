# 리팩터링과 코드 품질 (신뢰의 근거)

이 파일은 AI가 만든 코드가 블랙박스여도 신뢰받는 조건, 즉 상시 유지되는 품질 불변식과 그것을 되돌리는 주기적 리팩터링을 소유한다. 리팩터링은 선택이 아니라 케이던스다(근거는 방법론 정본 0절).

## 1. 품질 불변식 (매 증분 뒤에도 참이어야 하는 것)

방법론 정본 0절의 다섯 가치(일관성·무손실 플럼빙·안전성·직관성·가독성)를 실측 가능한 형태로 옮긴 것이 아래 불변식이다. 각 불변식은 실측할 수 있어야 한다. 도구가 있으면 도구로(중복 탐지기·의존성 규칙·린터·데드코드 탐지), 없으면 grep·삭제 테스트로.

| # | 불변식 | 실측 방법 |
|---|---|---|
| 1 | 중복 0: 같은 도메인 규칙에 복수 정본이 없다. 독립된 컨텍스트의 우연히 같은 형태는 억지로 합치지 않는다 | 중복 탐지 결과를 소유권·변경 이유와 대조 |
| 2 | 깊은 모듈: 계약·격리·호환 책임 없는 전달 계층이 없다. 구현 하나인 IO 포트도 현재 책임이 있으면 유지한다 | 삭제 시 계약과 테스트 격리가 보존되는지 검토 |
| 3 | 도메인 언어 일치: 식별자·테스트 이름·라벨이 용어집과 같다 | 용어집 대비 grep(금지 동의어 검색) |
| 4 | 최소 코드: 순증가한 줄마다 수용 기준으로 정당화된다 | diff 통계와 수용 기준 대응표 |
| 5 | 데드코드 0: 미사용 import·함수·상수·분기·죽은 배선이 없다 | 린터·미사용 탐지·소비자 추적 |
| 6 | 관심사 분리·한 방향 의존: 도메인이 IO를 모르고 순환이 없다 | 의존성 규칙 도구 또는 import 그래프 |
| 7 | 테스트 대응: 수용 기준마다 테스트가 있고, 테스트는 이음새에서만 | 인텐트 AI 판정 표 |
| 8 | 런타임 안전: 외부 입력·회복 가능한 오류가 처리되지 않은 패닉으로 종료되지 않고, 미완성 경로·디버그 잔여물이 없다 | 언어별 정적 검사와 오류 경로 테스트. Rust의 unwrap/expect/panic 및 unsafe 검색은 검토 후보 수집이며 자체로 안전성 증명이 아니다 |
| 9 | 구조 예측 가능성: 파일의 자리가 저장소 구조 규칙에서 자명하고, 빈 폴더·고아 파일·통칭 이름·잘못된 배치 레벨이 없다 | 코드 조직 정본의 구조 감사 표를 변경 반경에 적용 |

불변식이 하나라도 깨진 채로 증분을 완료로 선언하지 않는다. 범위 내 실제 위반과 미검증을 구분해 기록한다. `unsafe`는 [교차 품질](cross-cutting-quality.md)의 메모리·자원 효율 절 기준으로 검증하고 안전한 API로 감싼다. 저장소가 더 엄격한 금지를 정했다면 그 계약을 따른다. 주석·문자열·생성 코드의 검색 일치를 실행 경로 결함으로 오인하지 않는다.

## 2. 리팩터 3층 케이던스

| 층 | 언제 | 무엇을 |
|---|---|---|
| 사이클 | 매 RED→GREEN 뒤 | 방금 만든 것의 중복 제거·이름 명료화·책임 분리·죽은 경로 정리. 테스트는 green 유지 |
| 인텐트 | 인텐트 완료 직전 | 변경 반경 안의 보이스카우트 정리, 불변식 9개 실측, 리터럴 감사, 용어 drift 정합화 |
| 주기 | 인텐트 N개마다 또는 주기적으로(프로젝트 인텐트가 정함, 기본 5개·1주) | 아래 아키텍처 리뷰. 후보를 찾아 하나씩 별도 리팩터 인텐트로 |

- 사이클·인텐트 층은 요청 없이 항상 밟는다. 주기 층은 프로젝트 인텐트가 상시 승인했으면 묻지 않고 진행하고, 아니면 리팩터 인텐트 초안을 올려 사람이 승인한다.
- 리팩터는 동작을 보존한다. 관측 가능한 동작이 전후 같아야 하고, 동작 변경은 별도 인텐트다. 고정하는 테스트가 없으면 특성화 테스트를 먼저 추가한다. 옮기기 전후로 생산자→소비자 배선을 확인한다(플럼빙과 정합성 정본). 기능 변경과 섞지 않는 규칙은 루프 운영 정본의 변경 위생에 있다.
- 정리 대상은 코드뿐 아니라 문구·주석·문서·파일·폴더까지다. 현재 사용처와 보존 목적을 확인해 미사용 경로, 중복 설명, 낡은 호환층, 의미 없는 래퍼와 임시 잔여물을 제거한다. 폴더는 실제 책임과 변경 이유로 묶고, 보기 좋게 하려는 계층·별칭·빈 뼈대는 만들지 않는다. 폴더·파일 재배치는 코드 조직 정본의 재배치 절차를 따른다. 출처·계약·복구·검증 근거는 불필요한 레거시와 구분한다.

### 핵심 기능 보존 게이트

리팩터링의 성공 조건은 구조 개선과 기존 기능 보존이 함께 성립하는 것이다. 코드가 짧아지거나 테스트가 초록이어도 사용자가 하던 작업이 실패하면 회귀다.

- 변경 전 정상 동작하는 핵심 사용 흐름과 계약을 기준선으로 고정한다. 입력·출력뿐 아니라 기본값·선택한 연결·설정 적용·인증·상태 수명주기·후속 작업도 변경 반경에 포함한다.
- 정상인 핵심 로직의 의미를 정리 명목으로 바꾸지 않는다. 구조 이동은 최소 범위로 하고, 새로운 동작은 별도 요청·인텐트·증분으로 분리한다.
- 특성화 검사와 변경 후 같은 흐름의 비교가 먼저다. 배포·재기동 후 확인 방법은 QA와 검증 정본의 리팩터링·배포·재기동 후 QA 절에 있다.
- 기존 계약에 맞는 검사를 삭제하거나 기대값을 바꿔 회귀를 통과시키지 않는다.
- 회귀를 발견하면 추가 리팩터링을 멈춘다. 최초 단절 지점을 재현해 최소 수정 또는 승인 범위 안의 복구를 하고, 같은 핵심 흐름을 다시 통과시킨다. 복구되지 않은 기능을 완료로 보고하지 않는다.

## 3. 주기 아키텍처 리뷰

목적은 얕은 모듈을 깊게 만들고 엔트로피를 되돌리는 것이다. 구조 전체를 뒤엎는 일이 아니다.

1. 범위를 먼저 정한다. 최근 자주 바뀐 곳(`git log`의 hot spot)에 가중치를 둔다. 자주 바뀌는 곳을 깊게 만드는 것이 가장 이득이 크다. 사람이 방향을 줬으면 그것을 따른다.
2. 마찰을 찾는다. 한 개념을 이해하려고 여러 작은 모듈을 오가는 곳, 인터페이스가 구현만큼 복잡한 곳, 테스트를 위해 뽑아낸 순수 함수 뒤로 진짜 버그가 호출부에 숨은 곳(국소성 없음), 이음새를 넘어 새는 결합, 현재 인터페이스로 테스트하기 어려운 곳.
3. 삭제 테스트를 건다. 지우면 복잡도가 모이는가(제 몫), 그냥 옮겨지는가(패스스루).
4. 후보를 나열한다. 각 후보: 관련 모듈, 마찰의 이유, 바뀌는 것, 국소성·레버리지 관점의 이득, 테스트가 어떻게 좋아지는가, 추천 강도(강함/검토 가치/추측). 후보 목록은 AI 작업 문서이므로 스크래치에 둔다.
5. 하나씩 깊게 만든다. 후보 하나를 리팩터 인텐트로 세우고 특성화 테스트 → 리팩터 → 게이트를 밟는다. 옛 얕은 모듈의 단위 테스트는 깊어진 인터페이스의 테스트가 생기면 지운다(겹겹이 쌓지 않고 교체한다).

깊게 만들 때 의존성의 종류가 테스트 방법을 정한다: 프로세스 내 계산은 합쳐서 직접 테스트, 로컬 대체물이 있는 의존(임베디드 DB·인메모리 FS)은 대체물로, 내가 소유한 원격 서비스는 포트+어댑터(운영 어댑터와 인메모리 어댑터), 진짜 외부 서비스는 주입된 포트에 mock 어댑터.

## 4. 코드 스멜 기준선 (리뷰의 품질 축)

저장소가 문서화한 기준이 항상 우선하고, 아래는 저장소가 아무것도 정하지 않아도 적용하는 기준선이다. 각 항목은 판단이 필요한 신호이지 자동 위반이 아니며, 도구가 이미 잡는 것은 사람이 다시 보지 않는다.

- 불명확한 이름 → 이름을 고친다. 정직한 이름이 안 나오면 설계가 흐린 것.
- 중복 코드 → 공통 형태를 추출해 양쪽이 호출.
- 기능 욕심(남의 데이터를 더 많이 만지는 메서드) → 그 데이터 쪽으로 옮긴다.
- 데이터 뭉치(늘 같이 다니는 필드·인자) → 타입 하나로 묶는다.
- 원시 타입 집착 → 도메인 개념에 값 객체를 준다.
- 반복되는 switch → 다형성 또는 공유 map 하나.
- 산탄총 수술(한 변경이 여러 파일에 흩어짐) → 함께 바뀌는 것을 한 모듈로.
- 발산하는 변경(한 모듈이 여러 이유로 바뀜) → 이유별로 나눈다.
- 추측성 일반화 → 지운다. 실제 필요가 생길 때까지 인라인.
- 메시지 체인(`a.b().c().d()`) → 첫 객체의 메서드 하나 뒤로 숨긴다.
- 중개자(대부분 위임만 하는 것) → 지우고 직접 호출.
- 거부된 유산(상속받은 대부분을 무시하는 하위 타입) → 상속 대신 합성.

## 5. 부채

부채의 기록·우선순위·상환은 유지보수와 부트스트랩 정본의 기술 부채 취급 절이 소유한다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "동작하니 정리는 나중에" | AI가 고칠 때마다 잔여물이 쌓인다. 사이클 층은 매 GREEN 뒤 요청 없이 밟는다 |
| "리팩터하는 김에 이 동작도 고치자" | 동작 변경이 섞이면 회귀와 의도를 구분할 수 없다. 동작 변경은 별도 인텐트다 |
| "테스트가 없어도 단순 이동이라 안전하다" | 이동이 기본값·연결·수명주기를 바꾸는 일이 흔하다. 특성화 테스트를 먼저 둔다 |
| "기대값을 바꾸면 테스트가 통과한다" | 기존 계약에 맞는 검사를 바꿔 통과시키는 것은 회귀 은폐다 |
| "줄 수가 줄었으니 좋아졌다" | 짧음은 목표가 아니다. 국소성·레버리지·동작 보존으로 판정한다 |
| "이 코드는 내 취향이 아니다" | 이미 정확하고 명료한 코드는 보존한다. 취향 변경은 diff 오염이다 |

## 위험 신호

- 불변식이 깨진 채 완료 선언, 리팩터를 "나중에"로 미룸
- 동작 변경이 섞인 리팩터, 기능과 리팩터가 한 diff, 특성화 테스트 없는 레거시 리팩터
- 기대값을 바꿔 통과시킨 회귀, 회귀 발견 후에도 계속되는 리팩터
- 리뷰에서 이미 정확한 코드를 취향으로 바꿈
- 주기 리뷰 없이 엔트로피 방치, 옛 테스트를 지우지 않고 겹겹이 쌓음, 부채의 무기록 방치

## 종료 게이트

- [ ] 매 GREEN 뒤 사이클 층을 밟았고 테스트가 green으로 유지됐다
- [ ] 인텐트 완료 전 불변식 9개를 실측했고 범위 내 위반이 0건이다(미검증은 이유와 함께 분리 기록)
- [ ] 리팩터라면 핵심 흐름 기준선과 변경 후 비교가 같은 결과다
- [ ] 반경 밖 부채는 인텐트 `남은 것`에 기록됐다
- [ ] 주기 층 케이던스가 도래했다면 아키텍처 리뷰 후보가 리팩터 인텐트로 올라갔다
