# 진단과 디버깅 (Diagnosis & Debugging)

결함을 고치기 전에 원인을 확정하는 활동을 소유한다. 수정 절차(재현 테스트 → 최소 수정 → 회귀 고정)는 TDD와 구현 정본이 소유하고, 이 파일은 그 앞단, 증상에서 확정된 원인까지 가는 길을 소유한다. 원인을 모른 채 고친 수정은 증상을 옮길 뿐이다.

## 원칙: 추측이 아니라 관측

- 코드를 읽고 "여기가 문제일 것"이라 짐작하는 것은 가설이지 진단이 아니다. 가설은 실행·로그·상태 덤프 같은 관측으로 확인하거나 기각한다.
- 실제 코드 경로를 실행 로그로 확증한다. 머릿속·수동으로 재현해 본 결과가 아니라, 결함이 난 그 경로가 실제로 실행되며 남긴 로그·출력으로 원인을 확정한다. 비슷한 경로를 손으로 돌려 보고 "여기일 것"이라 단정하면 다른 코드 경로를 진단한 오진이 된다.
- 익숙한 실패와 패턴이 비슷해도 원인이 같다고 단정하지 않는다. 같은 증상에 다른 원인이 흔하다. 상관을 인과로 오인하지 않는다.
- 산출물이 진단인 경우(방법론 정본 3절)에는 원인·근거·영향을 보고하고, 수정 요청이 있을 때만 고친다.

## 절차

1. 증상을 정확히 적는다. 기대 동작 vs 실제 동작, 발생 조건(입력·환경·버전·시각), 재현 빈도(항상/간헐), 처음 나타난 시점. "안 된다"는 증상이 아니다.
2. 타이트하고 빨개질 수 있는 피드백 루프를 구축한다. 결함을 빠르고 결정론적으로 재현하는 루프가 있으면 원인은 반드시 규명된다. 루프가 없으면 코드를 아무리 읽어도 소용없다.
   - 수단(우선순위순): 실패 단위/통합/E2E 테스트 → 로컬 서버 대상 `curl`/HTTP 스크립트 → 픽스처 입력 기반 CLI stdout 스냅샷 diff → 헤드리스 브라우저 스크립트 → 캡처된 네트워크 트레이스·이벤트 페이로드 리플레이 → 최소 서브셋만 인메모리로 격리한 임시 하네스 → 무작위 입력 프로퍼티/퍼즈 루프 → 커밋 간 자동 이분 탐색(`git bisect run`) → 신/구 버전·두 설정 간 출력 차등 비교 → 캡처 출력이 피드백되는 쉘 스크립트.
   - 타이트화: 루프는 초 단위(2~3초)여야 한다. 결함 발생 경로만 남겨 캐시·초기화를 건너뛰고, "안 죽었다"가 아니라 "사용자의 정확한 증상"을 날카롭게 단언한다.
   - 간헐 결함의 재현율 증폭: 1% 확률의 버그는 디버깅 불가능하다. 100회 루프·병렬화·부하 주입·sleep 조정으로 재현율을 50% 이상으로 끌어올린다.
   - 관문: 재현 경로·입력·계측 지점을 찾기 위한 코드 읽기와 가설 수립은 먼저 할 수 있다. 관측 전 가설을 원인으로 확정하거나 근거 없이 수정하지 않는다. 재현이 어려우면 로그·트레이스·최소 하네스로 증거를 보강하고, 확인되지 않은 원인은 가설로 보고한다.
3. 재현 조건을 극소화한다. 빨간색을 본 즉시 입력·호출자·설정·데이터를 하나씩 깎아내어 재실행하고, 남은 모든 요소가 결함에 필수적인 최소 재현 조건을 확립한다. 이것이 가설 공간을 줄이고 정밀한 회귀 테스트가 된다.
4. 3~5개의 순위화된 반증 가능 가설을 세운다. 단일 가설은 첫 편향에 매몰된다. 각 가설은 "만약 <X>가 원인이라면, <Y를 변경>했을 때 증상이 사라지거나 악화될 것이다" 형식으로 예측을 진술해야 한다. 예측이 불가능한 가설은 느낌이므로 기각하거나 다듬는다.
5. 계측하고 국소화한다. 탐침은 4단계의 예측과 1:1로 대응하고, 한 번에 한 변수만 바꾼다. 차등(두 조건 비교)·이분(범위 절반씩)·계층 절단(경계에서 입출력 고정)으로 범위를 좁힌다.
   - 무작위 로그 남발을 금지한다. 가설을 가르는 경계에만 타깃 로그를 둔다.
   - 임시 로그에는 `[DEBUG-고유ID]` 접두사를 붙여 종료 시 `grep` 한 번으로 전수 제거가 보장되게 한다.
   - 성능 저하는 로그가 아니라 프로파일러·`performance.now()`·쿼리 플랜으로 기준 측정을 세우고 이분한다.
6. 원인을 확정한다. 가설이 확인되고, 원인을 제거하면 증상이 사라지며, 되돌리면 재발함을 보였을 때 확정이다. 확정된 원인은 TDD와 구현 정본의 근본 원인 수정으로 넘긴다.

## 소스 레벨 진단 로깅 (사후 분석성)

장애 뒤 로그만으로 어떤 입력이 왜 깨졌는지 추적·재현할 수 있도록 런타임 코어·외부 API 클라이언트·프로바이더 어댑터·파서·큐/버퍼·네트워크 경계에서 다음을 남긴다.

- 실패 지점 식별자·인덱스와 상관 ID
- 수신 원본의 앞부분 스니펫과 전체 길이
- 파싱·검증 실패의 구체 이유
- 공급자 응답의 종료 사유(finish_reason)·상태 코드
- 재시도 횟수와 상태 전이, 종료 사유

묵시적 침묵(silent drop)이나 "처리 실패"·"파싱 에러" 같은 추상 메시지로 넘기지 않는다. 같은 오류가 transcript·journal·prompt·UI에 중복 주입되어 노이즈로 증폭되지 않게 한다. 임시 디버그 로그와 달리 이것은 제품의 일부이며, 민감 데이터는 넣지 않는다.

## 기록

- 진단 결과는 증상 → 재현 조건 → 확정 원인 → 근거(관측) → 영향 범위로 압축해 보고한다(보고 정본). 기각한 가설은 한 줄씩 남긴다. 무기록이면 같은 시도를 반복한다.
- 원인이 재발 가능한 부류(설계 가정 붕괴·계약 불일치)면 사양·계획 정본의 가정 원장에 추가하고, 운영 장애였다면 사후 분석(유지보수와 부트스트랩 정본)으로 이어 간다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "코드를 보니 여기가 문제다" | 읽고 짐작한 것은 가설이다. 실제 경로의 로그·출력으로 확정한다 |
| "지난번이랑 똑같은 증상이다" | 같은 증상에 다른 원인이 흔하다. 이번 경로에서 다시 관측한다 |
| "재시도하니 통과했다" | 결함이 사라진 것이 아니라 관측을 놓친 것이다. 재현율을 끌어올린다 |
| "일단 여러 군데 고쳐 보자" | 한 번에 여러 변수를 바꾸면 무엇이 원인인지 영원히 모른다 |
| "재현 루프 만들 시간이 없다" | 루프 없이 읽는 시간이 더 길다. 초 단위로 빨개지는 루프가 가장 빠른 길이다 |

## 위험 신호

- 재현 루프 없이 코드부터 읽기, 재현 없이 추정으로 수정, 관측 없이 원인 단정
- 수동 재현으로 실제 코드 경로를 대신함, 한 번에 여러 변수 변경
- 가설 하나에 매달림, 예측이 없는 가설
- 증상만 숨기는 수정(TDD와 구현 정본의 금지 목록), 상관을 인과로 오인, 여러 원인의 중첩을 하나로 단정
- 실행 중인 산출물·환경이 소스와 같은지 확인하지 않음(논리 구멍 카탈로그의 실행 환경), 진단 대신 시스템 상태를 바꾸는 조치(방법론 정본 8절)
- 원인 확정 없이 "고쳐진 것 같다"로 보고, 기각 가설 무기록
- 재현 불가 결함을 관측 보강 없이 종료, 태그 없는 임시 로그

## 종료 게이트

- [ ] 증상이 기대·실제·조건·빈도로 적혀 있다
- [ ] 결함을 결정적으로 재현하는 루프가 있다(간헐이면 재현율을 측정했다)
- [ ] 원인을 제거하면 증상이 사라지고 되돌리면 재발함을 보였다. 아니면 가설로 보고했다
- [ ] 기각 가설이 한 줄씩 남았고, `[DEBUG-` 임시 로그가 grep 0건이다
