# QA와 검증 (위상 5)

완료를 선언하기 전에 실행하는 검증 파이프라인을 소유한다. 실측 없이는 완료 없다. 실행되지 않은 검증은 통과와 실패를 구별하지 못한다.

## 절차

1. 배선 추적이 보인 파급 범위로 검증 단계(초점 → 공유 계약 → 전체)를 정한다.
2. 저장소가 지정한 방식으로 게이트를 실행하고 명령·종료 코드·개수를 기록한다.
3. 여러 단계가 한 사용자 목표를 이루면 실제 진입점에서 기능 체인을 한 번에 실행한다.
4. 전수 감사와 논리 구멍 카탈로그로 사각지대를 훑는다.
5. 새로 만든 검사는 실제로 무엇을 재는지 확인한다.
6. 수용 기준마다 증거를 인텐트의 AI 판정에 적는다. 실행하지 못한 것은 이유와 함께 미검증으로 남긴다.

## 증거 기반 (호언장담 금지)

- "완벽하게 고쳤다", "모든 문제가 해결됐다" 같은 근거 없는 완료 선언을 금지한다.
- 모든 상태·완료 주장에 물리적 증적을 첨부한다: 실제 명령, 실행 로그, 통과/실패 개수, 종료 코드, 실측 수치. "될 것"이라는 추론으로 대체하지 않는다.

## 저장소 게이트 실측 실행

- 저장소 운영 계약(`AGENTS.md`/`CLAUDE.md`/README)이 빌드·테스트·린트·포맷·타입체크를 특정 명령·스크립트·격리 환경으로만 하라고 하면 그 방식으로만 실행한다.
- 무거운 빌드·테스트를 임의로 host에서 병렬로 돌려 리소스 락 충돌이나 시스템 불안정을 유발하지 않는다. 순차 실행·리소스 상한 요구를 따른다.
- 게이트를 실행할 수 없으면(환경·권한·상한) 그 사실과 정확한 명령을 남기고 사용자에게 직접 실행을 요청할 수 있다.
- 같은 게이트를 무한 재시도하지 않는다. 저장소가 상한(예: 3회)을 두면 따르고, 실패가 이번 변경과 무관하면 임의로 고치지 말고 blocker로 보고한다.

## 검증 범위 (초점 → 공유 계약 → 전체)

검증의 강도·범위는 영향 범위와 위험도에 비례한다. 모든 변경에 전체 게이트를 습관적으로 돌리는 것은 낭비이고, 공유 계약 변경을 국소 검증으로 끝내는 것은 누락이다.

1. 초점 검증: 수정한 모듈·패키지의 단위·통합 테스트를 먼저 돌린다. 파급이 모듈 안에서 끝나는 변경은 여기서 끝나도 되며, 그 판정의 근거(배선 추적)를 남긴다.
2. 공유 계약 검증: 여러 소비자가 공유하는 계약(타입·API·스키마·스냅샷)을 바꿨으면 그 계약의 전체 게이트를 돌린다.
3. 전체 게이트: 릴리스나 광범위 변경은 저장소의 전체 검증(빌드·테스트·린트·포맷·타입체크·정책·감사)을 저장소 지시대로 순차·상한 실행한다.

## 기능 체인 검증

여러 단계가 한 사용자 목표를 이루는 기능은 분리된 초록불의 합으로 완료 판정하지 않는다. 동일한 실제 입력과 상관 ID·리비전을 보존한 채 공개 진입점부터 최종 외부 결과까지 한 번의 체인으로 실행한다.

- 수용 기준의 순서대로 요구 해석 → 도메인 처리·구현 → 저장소 게이트와 데이터 검증 → 미리보기·전달 → 사용자가 요청한 게시·부작용까지 관측한다. 해당하지 않는 단계는 빼되 중간 단계를 가짜 성공으로 대체하지 않는다.
- 입력·상태·산출물의 동일성을 단계 경계마다 확인한다. 서로 다른 fixture, 수동으로 만든 중간 산출물, 별도 요청의 성공을 한 체인의 증거로 합치지 않는다.
- 성공뿐 아니라 해당하는 실패·타임아웃·취소·재시도·중복 요청에서 입력 보존, truthful state, 멱등성, 복구와 임시 자원 회수를 확인한다.
- 실패하면 최초 단절 지점의 원인을 고치고 같은 체인을 처음부터 재실행한다. 후속 단계를 개별 호출해 녹색으로 만드는 것은 완료 증거가 아니다.

단위·통합·계약 테스트는 체인의 각 경계를 빠르게 반증하고 회귀를 막는다. E2E 기능 체인은 그 경계들이 실제 배선으로 조립되어 사용자 목표를 달성하는지 증명한다. 둘 중 하나도 다른 하나를 대체하지 않는다.

### 리팩터링·배포·재기동 후 QA

- 변경 전 기준선과 같은 공개 진입점·입력·설정으로 핵심 작업을 실행하고, 최종 결과와 후속 작업까지 확인한다. 선택한 설정이 실제 실행 경로에 적용되는지도 관측한다.
- 배포·재기동을 했으면 갱신된 인스턴스에서 같은 흐름을 다시 실행한다. 재기동 전 테스트를 재기동 후 성공의 증거로 쓰지 않으며, 필요한 사용자 상태·설정·인증의 유지 여부를 확인한다.
- 빌드 성공·컨테이너 healthy·HTTP 200·로그인 상태·별도 연결 시험은 각각의 경계만 증명한다. 실제 요청 실행과 결과 수신을 확인하기 전에는 핵심 기능이 정상이라고 보고하지 않는다.
- 외부 연동이 핵심 작업에 포함되면 승인된 실제 연동 경로도 검증한다. 대역은 계약 검증의 증거이지 실제 연동 성공의 증거가 아니다. 실연동을 실행할 수 없으면 대역 통과와 실연동 미검증을 분리하고 해당 기능을 완료로 선언하지 않는다.
- 보고에는 변경 전후 비교, 실행한 실제 흐름, 실패·건너뜀·미검증을 구분해 남긴다. 회귀가 있으면 [핵심 기능 보존 게이트](refactoring-and-code-quality.md)를 따른다.

## 전수 감사 (Zero-Omission Audit)

단편적 부분 수정에 그치지 않고 연관된 모든 상·하위 모듈의 호출부와 엣지를 누락 없이 점검한다.

- 런타임 안전은 [품질 불변식](refactoring-and-code-quality.md)의 기준으로 판정한다. 해당 언어의 린터·타입 검사로 후보를 찾고 실제 오류 경로를 실행한다. 제품의 정상 CLI 출력과 임시 디버그 출력을 구분하고 TUI 렌더링을 방해하는 날것 출력을 제거한다.
- 자율 루프 픽스처 완결성: 자율 드라이버가 있는 런타임 테스트는 피검증 워커뿐 아니라 드라이버의 종료 경로를 픽스처에 명시한다. 드라이버가 끝나지 않으면 유휴 대기가 타임아웃되어 비결정적 실패가 된다.
- 다중 런타임 정합성: 플럼빙과 정합성 정본의 반경 내 동기화 대상(매니페스트·락파일·컨테이너·빌드 래퍼·배포 번들)이 실제로 일치하는지 실측한다.
- 아키텍처 감사: 처리되지 않은 오류 경로와 새는 추상화가 없는지. 배선은 플럼빙과 정합성 정본의 추적 결과를 쓴다.
- 회귀·리소스 안전: 연관 서브시스템이 안정적이고, 메모리·동시성 계약이 보존되며, 승인되지 않은 동작 변경이 없는지.
- 잠재 결함 전수: 미사용 import·함수·상수, 대소문자 단언 오류, 경계 침범(뷰포트·버퍼). 사소한 가정은 논리 구멍 카탈로그를 실제로 훑는다.

## 검사가 실제로 재는지 검증 (Meta-verification)

돌면서 아무것도 보지 않는 검사는 죽은 검사와 구별되지 않으면서 초록불로 남는다. 새로 만든 검사는 자기가 무엇을 재는지 증명할 수 있어야 한다.

- 검사가 실제로 실행되는지 확인한다. 중간에서 죽고 뒤가 실행되지 않는 스크립트, `package.json`에 항목이 없어 문서에만 존재하는 검사는 통과가 아니라 부재다.
- 절반만 돌고 성공하는 것을 불가능하게 한다. 검사가 자기 구간을 선언하고 끝에서 전부 실행됐는지 대조하게 만든다. 미결 장부가 남으면 명시적 성공조차 실패로 뒤집는다.
- "없어야 한다"는 "있어야 한다"의 짝을 갖는다. 부재 확인은 읽기가 빈손이면 저절로 참이 되므로, 같은 읽기가 대상이 있는 곳에서 정확히 하나를 세는 것을 함께 주장한다.
- 조건과 무관한 상수를 읽는 검사, 정규식 갈래를 다 지워도 통과하는 검사, 문자열에 규칙이 있는지만 읽고 화면에서 보이는지는 안 보는 검사를 만들지 않는다.

## 성능 개선 검증

성능 주장은 교차 품질 정본의 성능 공학 절의 측정 조건으로 전·후를 실측한 수치로만 한다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "빌드가 되고 컨테이너가 healthy다" | 각각의 경계만 증명한다. 실제 요청을 보내고 결과를 받기 전에는 정상이 아니다 |
| "단위 테스트가 다 통과했다" | 분리된 초록의 합은 조립된 기능의 증거가 아니다. 기능 체인을 실행한다 |
| "mock으로 연동을 확인했다" | 대역은 계약의 증거다. 실연동 미검증은 미검증으로 보고한다 |
| "이 실패는 원래 깨져 있던 것이다" | 기준선이 있어야 그 말을 증명할 수 있다. 증거와 함께 블로커로 기록한다 |
| "전체 게이트는 오래 걸리니 생략한다" | 공유 계약을 건드렸으면 그 계약의 전체 게이트가 필요하다. 범위는 추적이 정한다 |
| "새 검사를 추가했으니 안전하다" | 아무것도 재지 않는 검사도 초록으로 남는다. 대상이 있는 곳에서 실패하는지 확인한다 |

## 위험 신호

- 실행 로그·수치 없는 완료 주장, "될 것이다"로 대체한 검증
- 저장소 지정 방식이 아닌 게이트 실행, 무한 재시도, 무관한 실패를 임의 수정
- 서로 다른 입력·fixture를 이어 붙인 체인 증거, 재기동 전 테스트로 재기동 후를 주장
- 대역 통과를 실연동 성공으로 보고
- 부재만 단독 확인하는 검사, 절반만 돌고 성공하는 스크립트
- 측정 없는 성능 개선 주장

## 종료 게이트

- [ ] 저장소 게이트를 지정 방식으로 실측했고 명령·결과가 기록됐다
- [ ] 다단계 기능은 실제 진입점에서 같은 입력·리비전으로 끝까지 실행됐다
- [ ] 전수 감사와 논리 구멍 훑기에서 누락이 없다
- [ ] 새 검사가 실제로 무엇을 재는지 증명됐다
- [ ] 리팩터·배포·재기동이면 같은 흐름의 전후 비교와 갱신된 인스턴스 확인이 있다
- [ ] 모든 주장에 증거가 붙었고, 미검증은 이유와 함께 분리됐다
