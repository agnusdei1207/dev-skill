# 인텐트와 프로젝트 docs (사람이 보는 표면)

이 파일은 사람과 AI 사이의 계약 문서인 인텐트(Intent)와, 그것이 사는 프로젝트 `docs/`의 구조를 소유한다. 사람은 `docs/`만 읽고 코드는 읽지 않는다. 계획·원장·구현 결정은 AI의 것이며, 그 일이 믿을 만한지는 문서가 아니라 인텐트 충실도의 증거와 코드 품질 불변식(리팩터링·코드 품질 정본)이 증명한다.

## 왜 인텐트인가

- 인텐트는 무엇을 왜 원하는가와 완료 증거를 연결한다. 기존 ADR·사고 기록이 결정의 정본이면 인텐트에서 링크하고 복제하지 않는다. 신규 결정의 위치는 저장소 관례를 따른다. 사람은 인텐트를 진입점으로 필요한 근거만 읽을 수 있어야 한다.
- 사람의 두 질문(방법론 정본 1절)에 답할 수 있게 `docs/`를 설계한다.
- 사람용 문서는 사람이 실제로 여는 위치에 둔다: 프로젝트 `docs/`. 숨은 폴더, 이슈 트래커, 스크래치 관례처럼 사람이 못 보는 곳에 두지 않는다.

## `docs/` 구조

```text
docs/
  intents/
    00-project.md        프로젝트 인텐트: 목적, 장기 제약, 영구 결정, 상시 승인 범위
    0001-<슬러그>.md      작업 인텐트: 한 번의 변경이 원하는 결과와 수용 기준
    0002-...
  GLOSSARY.md            용어집: 인텐트·코드·테스트·UI가 쓰는 한 언어 (형식·분할은 도메인 모델링 정본)
  ARCHITECTURE.md        구조 지도: 지금 코드가 어떤 모듈로 이뤄져 있고 각각 왜 있는가, 컨텍스트 맵
```

- 번호는 시간 순서다. 폴더 목록만 훑어도 무엇이 언제 있었는지 읽힌다. 완료된 인텐트는 지우지 않는다.
- 구조 지도는 생성된 코드를 사람이 읽을 수 있게 정리한 것이다. 항목마다 `모듈(또는 바운디드 컨텍스트) — 책임 한 줄 — 공개 인터페이스 요지 — 근거 인텐트 번호`를 적는다. 한 화면 안에 들어가게 유지하고, 코드를 복제하거나 파일 목록을 나열하지 않는다. 코드 구조가 바뀌면 같은 커밋에서 갱신한다. 사람은 이 지도로 첫 번째 질문(방향)에 답한다.
- 세 문서는 각각 단일 정본이며 서로 복제하지 않는다. 필요한 조각만 로드되도록 작고 독립적으로 쓴다(방법론 정본의 컨텍스트 엔지니어링).
- 저장소에 이미 ADR·런북·사고 기록이 있으면 원본과 이력을 보존하고 세 역할에서 링크한다. 역할은 탐색 관점이지 파일 형식 강제가 아니다. 문서 이관·폐기는 사용자가 해당 범위를 요청했을 때만 별도 변경으로 수행하며, 보호된 기록은 수정하지 않는다.

## 인텐트 형식

```markdown
# INTENT-NNNN · <제목>
- 상태: 초안 | 진행 중 | 완료 | 보류      ← AI가 갱신
- 작성 / 갱신 날짜

## 왜
지금 무엇이 문제이고, 이것이 되면 무엇이 가능해지는가. 처음 보는 사람 눈높이로.

## 무엇
사용자 관점에서 원하는 결과. 구현이 아니라 관측 가능한 행동.

## 수용 기준
- [ ] 관측되면 완료인 문장 (입력 A → 결과 B)      ← AI가 증거와 함께 체크

## 제약
지켜야 할 것: 성능·비용·플랫폼·호환·규제·마감, 건드리지 않을 경로.

## 비범위
이번에 하지 않을 것.

## 열린 질문 → 결정
- Q: <사람만 답할 수 있는 질문> — 선택지·트레이드오프·추천
- 결정: <사람의 답 한 줄과 이유>

---
## AI 판정                                          ← 아래는 AI가 채운다
| 수용 기준 | 증거(테스트·명령·수치) | 판정 |
구조 지도 변경 / 남은 것 / 남는 위험 / 발견한 부채
```

상단은 사람이 쓰고 AI는 고치지 않는다(용어 정합화와 오탈자 제외). 하단은 AI가 채우고 사람은 읽기만 한다. 프로젝트 인텐트는 `왜·제약·결정·상시 승인 범위`만 가지며 수용 기준과 AI 판정이 없다.

## 인텐트를 세우는 법 (요구 도출)

사람의 첫 요청은 인텐트의 재료이지 인텐트가 아니다. 인텐트가 없거나 비어 있으면 AI가 초안을 만들고 사람이 승인한다.

- 표면이 아니라 목적을 읽는다. "X를 고쳐 달라"의 목적이 "Y가 되게"이면 수용 기준은 Y다.
- 수용 기준은 검증 가능한 문장이다. "동작한다"가 아니라 "입력 A에 결과 B, 게이트 G 종료 코드 0". 검증할 수 없는 기준은 기준이 아니다.
- 이해관계자와 실제 필요를 구분한다. 요청자가 말한 해법 뒤의 필요를 찾고, 필요 없는 기능(gold-plating)은 비범위로 보낸다.
- 모호함은 질문으로 닫는다. 서로 다른 해석이 실질적으로 다른 산출물을 낳을 때만 `열린 질문`에 올린다. 질문은 선택지·트레이드오프·추천을 갖춘 결정 요청이어야 한다(보고 정본). 그 밖의 해석은 신중한 동료가 하듯 스스로 정하고 진행한다.
- 용어를 먼저 확정한다. 인텐트가 다루는 개념마다 용어집의 한 단어를 쓴다(도메인 모델링 정본의 유비쿼터스 언어).
- 추적성. 수용 기준마다 최소 한 개의 테스트가 대응한다. 대응하지 않는 기준은 검증되지 않은 것이고, 어떤 기준에도 대응하지 않는 코드는 요청되지 않은 것이다.

### 인텐트 인터뷰

해석이 실질적으로 갈리거나 위험도가 MED 이상이면, 초안을 쓰기 전에 사람과 짧은 인터뷰로 결정 트리의 가지를 닫는다. 목적은 원하는 것과 만들어질 것 사이의 틈을 구현 전에 없애는 것이다.

1. 스스로 답할 수 있는 것은 묻지 않는다. 코드·`docs/`·커밋 이력·실행 결과로 확인 가능한 사실은 먼저 확인하고, 확인한 내용을 질문의 전제로 쓴다.
2. 결정 트리를 세운다. 목적 → 행위자 → 관측 가능한 성공 → 범위 경계 → 실패·엣지 → 제약 → 비범위 순서로 가지를 나눈다. 위 가지가 정해져야 아래 가지의 질문이 의미를 갖는다.
3. 한 번에 하나만 묻는다. 질문마다 선택지, 각각의 트레이드오프, 추천 답과 이유를 붙여 사람이 고르기만 하면 되게 한다.
4. 단어를 즉시 다룬다. 답에 나온 단어가 용어집과 충돌하거나 모호하면 그 자리에서 드러내고 정확한 용어를 제안해 확정한다(도메인 모델링 정본).
5. 구체 시나리오로 경계를 강제한다. "같은 요청이 두 번 오면?", "목록이 비어 있으면?"처럼 엣지 사례를 제시해 추상적 동의가 아닌 구체 결정을 받는다.
6. 답은 바로 인텐트 초안에 흡수한다. 모든 가지가 결정되거나, 남은 가지가 되돌릴 수 있는 가정으로 표시되면 인터뷰를 끝낸다.

인터뷰의 길이는 위험도가 정한다. LOW는 질문 없이 가정을 명시하고 진행하며, HIGH는 일방향 문에 닿는 가지를 모두 닫는다. 되돌릴 수 있는 세부를 묻느라 진행을 멈추지 않는다(루프 운영 정본의 자율 실행 원칙).

## 결정은 인텐트로 돌아간다

- 되돌리기 어려운 결정(일방향 문)은 AI가 정하지 않는다. `열린 질문`에 올리고 사람의 답을 `결정`에 한 줄로 흡수한다. 여러 작업에 걸쳐 살아남는 결정은 프로젝트 인텐트의 `제약`으로 올린다.
- 되돌릴 수 있는 결정(양방향 문)은 AI가 정하고 진행한다. 기록은 커밋 메시지의 "왜"로 충분하다.
- 놀라운 코드 선택(읽는 사람이 "왜 이렇게?"라고 물을 곳)은 그 자리에 `왜` 주석 한 줄을 남기고 인텐트 번호를 적는다. 별도 문서를 만들지 않는다.
- 사소한 결정도 결정이다. 판단은 내리고 기록 비용만 줄인다(진행 중에는 루프 운영 정본의 Ruling 한 줄). 무기록이 쌓이면 아무도 현재 상태를 설명하지 못한다.
- 별도 기록(인텐트 `결정`·프로젝트 인텐트 `제약`·저장소의 ADR)은 세 조건이 모두 참일 때만 남긴다: 되돌리기 어렵다, 맥락 없는 다음 독자가 놀랄 것이다, 실제 대안 사이의 트레이드오프에서 나왔다. 하나라도 거짓이면 커밋 메시지의 "왜"로 충분하다.

## 상태 갱신 규율 (AI 판정 절은 살아 있는 원장이다)

- 증분을 ship할 때마다 `AI 판정`과 구조 지도를 같은 변경에서 코드와 1:1로 맞춘다. 코드가 앞서고 문서가 뒤처지면 그 문서는 거짓 신호다.
- 체크박스의 `[x]`는 실행된 테스트·명령의 증거를 뜻한다. 확인하지 않은 기준을 체크하지 않는다.
- 상태를 `완료`로 올리는 조건은 완료 체크리스트 정본의 완료 정의다. 하나라도 남으면 `진행 중`으로 두고 남은 것을 적는다.
- 작업 중 발견한 반경 밖 부채·위험은 `남은 것`에 적는다(유지보수 정본의 기술 부채 취급).

## AI 작업 문서는 휘발성이다

계획, 프리플라이트 표, 진행 원장, 채점표는 AI가 일하기 위한 문서다. 세션 스크래치에 두고 저장소에 커밋하지 않는다. 저장소에 남는 것은 `docs/`(인텐트·용어집·구조 지도) + 코드 + 테스트 + 원자 커밋뿐이며, 작업의 흐름은 Git history가 보존한다. 세션이 끊겨도 이어서 일할 수 있게 하는 것은 인텐트의 `AI 판정`과 `남은 것`이다.

## 핑계와 반박

인텐트 없이 구현하지 않는다.

| 핑계 | 반박 |
|---|---|
| "요청이 분명하니 인텐트는 생략한다" | 분명해 보이는 요청일수록 성공 기준이 머릿속에만 있다. 작은 변경은 몇 줄로 압축한다 |
| "이건 내가 정해도 되겠지" | 되돌리기 어려운 결정은 사람의 몫이다. 선택지·트레이드오프·추천을 열린 질문으로 올린다 |
| "질문을 많이 하면 귀찮아한다" | 질문 수가 아니라 질문 품질이 문제다. 스스로 확인할 것은 확인하고, 추천 답이 붙은 질문을 하나씩만 한다 |
| "AI 판정은 마지막에 한꺼번에 채운다" | 코드가 앞서고 문서가 뒤처지는 순간 문서는 거짓 신호다. 증분마다 같은 변경에서 갱신한다 |
| "거의 통과했으니 체크한다" | `[x]`는 실행 증거를 뜻한다. 확인하지 않은 기준은 체크하지 않는다 |

## 위험 신호

- 검증 불가한 수용 기준("잘 동작한다", "빠르다")
- 사람 몫의 결정을 AI가 내림, 열린 질문 없이 통과한 일방향 문
- 증거 없는 `[x]`, 코드와 어긋난 AI 판정이나 구조 지도
- 파일 목록·코드 복제로 부풀린 구조 지도
- 사람이 못 보는 곳에 둔 사람용 문서, 계획·원장을 저장소에 쌓음
- 인텐트에 없는 기능을 조용히 추가함
- 코드로 확인할 수 있는 사실을 사람에게 물음, 추천 없이 "어떻게 할까요?"로 끝나는 질문

## 종료 게이트

- [ ] 인텐트가 있고(작은 변경은 몇 줄 압축), 수용 기준이 모두 관측 가능한 문장이다
- [ ] 해석이 갈리는 가지는 인터뷰로 결정됐거나 되돌릴 수 있는 가정으로 표시됐다
- [ ] 일방향 결정은 사람의 답이 `결정`에 있다
- [ ] 수용 기준마다 대응 테스트가 AI 판정 표에 증거와 함께 있다
- [ ] AI 판정·구조 지도·용어집이 코드와 같은 변경에서 갱신됐다
