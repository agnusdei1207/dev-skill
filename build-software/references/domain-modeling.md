# 도메인 모델링 (DDD)

이 파일은 코드가 도메인의 언어와 규칙을 그대로 담게 하는 방법을 소유한다: 유비쿼터스 언어와 용어집, 하위 도메인 분류, 바운디드 컨텍스트와 컨텍스트 맵, 전술 패턴(엔티티·값 객체·애그리거트·도메인 이벤트·서비스·리포지토리), 모델링 세션 절차. 모듈·폴더·파일 배치는 코드 조직 정본이, 서비스 분리·데이터 모델·API 계약은 설계 정본이 소유한다. 목표는 사람이 인텐트를 읽고 코드에서 같은 단어를 찾아, 규칙이 어디서 지켜지는지 예측하는 상태다.

## 적용 강도

DDD는 복잡한 도메인 규칙을 다루는 도구이지 모든 코드에 붙이는 의례가 아니다. 철학(Simple is best)이 우선한다.

| 도메인 성격 | 적용 |
|---|---|
| 규칙이 거의 없는 CRUD·설정·관리 화면 | 유비쿼터스 언어만. 전술 패턴·계층 분리를 만들지 않는다 |
| 규칙·상태 전이·불변식이 있는 영역 | 언어 + 불변식 소유자 + 값 객체 + 필요한 애그리거트 |
| 같은 단어가 영역마다 다른 뜻, 팀·배포 경계가 갈림 | 위 전부 + 바운디드 컨텍스트 분리와 컨텍스트 맵 |

판정 기준은 규칙의 양과 변경 빈도다. 규칙이 생기기 전에 애그리거트·리포지토리·팩토리 계층을 미리 깔지 않는다. 규칙이 생기면 그때 모델로 끌어올린다.

## 1. 유비쿼터스 언어 (한 개념 = 한 단어)

- 용어집 `docs/GLOSSARY.md`가 정본이다. 항목 형식: `용어 — 정의 — 코드 식별자 — UI 라벨 — 쓰지 않는 동의어`. 정의는 무엇인지(IS)를 한두 문장으로, 구현 세부 없이 쓴다. 용어집은 사양·스크래치·구현 결정 기록이 아니다.
- 인텐트·코드·테스트·UI·문서가 같은 단어를 쓴다. 같은 것을 `user`/`account`/`member`로, `delete`/`remove`/`destroy`로 흩뿌리지 않는다. 코드에선 `report`인데 화면에선 "문서"이면 정합성 결함이다(의도된 현지화 매핑은 명시).
- 이름을 짓기 전에 용어집을 읽고 그 용어만 쓴다. 새 개념은 기존 항목과 겹치지 않는지 확인한 뒤 용어집에 먼저 등록하고, 그다음 코드에 쓴다. 코드에 먼저 박힌 임의 용어는 나중에 전수 rename을 부른다.
- 용어집에는 이 프로젝트 고유 개념만 둔다. 타임아웃·에러 타입·유틸 같은 일반 프로그래밍 개념은 넣지 않는다. 용어집 파일은 첫 용어가 확정될 때 만든다.
- 한 개념은 모든 표면에서 한 이름이다. 코드 식별자, API 필드, DB 컬럼, UI 라벨, 로그·에러 문구, 문서, 언어별 번역까지가 그 개념의 표면이고, 번역본은 원문의 요약이 아니라 대응본이다. 이름을 바꾸면 용어집을 먼저 고치고 나머지 표면을 같은 변경 안에서 전수 검색해 맞춘다. 용어가 흔들리면 국소 수정을 멈추고 어휘부터 정합화한다.
- 모델은 도메인 행위로 말한다. `setStatus("cancelled")`가 아니라 `cancel(reason)`, `updateOrder`가 아니라 `addLine`·`applyCoupon`. 메서드 이름이 도메인 전문가의 동사와 같아야 규칙이 그 메서드 안에 모인다.

## 2. 하위 도메인 분류 (어디에 투자하는가)

제품을 하위 도메인으로 나누고 각각의 투자 수준을 정한다. 이 분류는 프로젝트 인텐트의 제약에 한 줄씩 남긴다.

| 분류 | 의미 | 투자 |
|---|---|---|
| 핵심(core) | 이 제품이 경쟁하는 이유. 규칙이 독자적이고 자주 바뀐다 | 직접 구현, 가장 풍부한 모델과 테스트, 최고의 이름 |
| 지원(supporting) | 핵심을 돕지만 차별점은 아니다 | 단순하게 직접 구현. 전술 패턴은 규칙이 있을 때만 |
| 일반(generic) | 누구나 같은 방식으로 푸는 문제(인증, 결제, 메일, 검색) | 검증된 라이브러리·서비스를 도입하고 경계에서 감싼다 |

일반 하위 도메인을 직접 만들거나, 핵심 하위 도메인을 프레임워크 기본값에 맡기는 것이 둘 다 실패다. 일반 도메인의 도입 판정은 교차 품질 정본의 도입 판정 절을 따른다.

## 3. 바운디드 컨텍스트

- 컨텍스트 하나에 언어 하나. 같은 단어가 영역마다 다른 뜻이면(주문의 "고객"과 결제의 "고객") 컨텍스트가 둘이다.
- 경계 식별 신호: 같은 단어의 정의가 둘로 갈린다, 한 개념의 속성 대부분을 어떤 영역은 전혀 쓰지 않는다, 변경 이유·변경 주기·담당자가 다르다, 정합성 요구가 다르다(즉시 vs 결과적).
- 경계를 성급히 긋지 않는다. 신호가 하나뿐이면 모듈 안의 명확한 이름으로 충분하다. 잘못 나눈 경계를 다시 합치기가 나중에 나누기보다 어려우므로, 확신이 없으면 하나로 두고 신호가 쌓일 때 나눈다.
- 모듈·패키지 경계는 컨텍스트 경계를 따른다. 컨텍스트가 곧 코드 조직 정본의 최상위 모듈이다.
- 컨텍스트가 여럿이면 용어집도 나눈다. `docs/GLOSSARY.md`는 컨텍스트 목록·관계와 각 컨텍스트 용어집(`docs/glossary/<context>.md`)으로의 링크만 가진다. 공통 개념은 공유 커널 용어집 하나에 둔다.

### 컨텍스트 맵

컨텍스트 사이의 관계를 이름으로 정하고 구조 지도(`docs/ARCHITECTURE.md`)의 한 절에 적는다. 관계가 정해져야 누가 계약을 바꿀 수 있는지가 정해진다.

| 관계 | 언제 | 코드에 나타나는 모양 |
|---|---|---|
| 고객-공급자 | 하류가 상류의 우선순위에 영향을 줄 수 있다 | 상류가 소유한 계약 + 하류의 계약 테스트 |
| 순응자 | 상류가 하류를 신경 쓰지 않고, 그 모델이 쓸 만하다 | 상류 모델을 그대로 사용 |
| 부패 방지 계층(ACL) | 상류 모델이 내 언어를 오염시킨다(레거시·외부 API) | 경계의 변환기. 내부에는 내 타입만 |
| 공개 호스트 서비스 + 공표된 언어 | 소비자가 여럿이다 | 버전 관리되는 공개 API·이벤트 스키마 |
| 공유 커널 | 두 컨텍스트가 작은 모델을 정말 공유한다 | 작게 유지하는 공유 모듈, 변경은 양쪽 합의 |
| 분리된 길 | 통합 비용이 이득보다 크다 | 통합 없음. 필요하면 사람이 잇는다 |

- 컨텍스트 간 교류는 명시적 계약으로만 한다. 다른 컨텍스트의 내부 모델을 직접 import하지 않고, 공개 표면·이벤트·ID 참조로 넘긴다.
- 다른 컨텍스트의 테이블을 직접 읽거나 쓰지 않는다. 공유 DB 테이블은 보이지 않는 공유 커널이며 두 컨텍스트를 함께 묶는다.

## 4. 전술 패턴

### 엔티티와 값 객체

- 식별자로 구별되고 수명 동안 상태가 바뀌는 것은 엔티티다. 같은 값이면 같은 것은 값 객체다.
- 값 객체를 기본으로 생각한다. 금액·기간·주소·이메일·수량·좌표·식별자는 원시 타입이 아니라 값 객체다. 값 객체는 불변이고, 생성 시 자기 유효성을 검증하며(유효하지 않은 값 객체는 존재할 수 없다), 연산(`money.add(other)`)을 스스로 가진다.
- 엔티티의 동일성은 식별자로만 판단한다. 식별자는 전용 타입(`OrderId`)으로 섞임을 막는다.

### 애그리거트

함께 즉시 일관돼야 하는 엔티티·값 객체의 묶음이다. 경계는 불변식이 정한다.

1. 불변식부터 적는다. "주문 총액은 항목 합과 같다", "확정된 주문의 항목은 바뀌지 않는다". 같은 트랜잭션 안에서 반드시 참이어야 하는 규칙만 애그리거트 경계 안에 둔다.
2. 작게 만든다. 루트 엔티티 하나와 그 불변식에 꼭 필요한 것만 넣는다. "관련 있어 보이는" 것을 모두 넣은 거대 애그리거트는 잠금 경합과 느린 로딩을 만든다.
3. 바깥에서는 루트만 만진다. 내부 엔티티를 밖으로 내주지 않고, 상태 변경은 루트의 도메인 메서드로만 한다. 루트가 불변식을 지키는 유일한 소유자다.
4. 다른 애그리거트는 ID로 참조한다. 객체 참조로 엮으면 경계가 사라지고 한 번의 로딩이 그래프 전체를 끌고 온다.
5. 한 트랜잭션은 애그리거트 하나만 바꾼다. 여러 애그리거트에 걸친 규칙은 도메인 이벤트로 결과적 정합성을 설계한다. 즉시 정합이 정말 필요하면 경계를 잘못 그은 것인지 먼저 의심한다.
6. 동시 수정은 버전 필드로 막는다(낙관적 잠금). 마지막 쓰기가 조용히 이기지 않게 한다.

### 도메인 이벤트

- 도메인에서 일어난 의미 있는 사실을 과거형으로 이름 짓는다(`OrderPlaced`, `PaymentFailed`). 명령(`PlaceOrder`)과 구분한다.
- 이벤트는 불변이고, 소비자가 재조회 없이 처리할 만큼의 사실과 발생 시각·식별자를 담는다. 내부 엔티티 전체를 직렬화해 싣지 않는다.
- 상태 변경과 이벤트 발행이 함께 성공하거나 함께 실패하게 한다(아웃박스 등). 저장은 됐는데 발행이 사라지거나, 발행은 됐는데 저장이 롤백되는 틈이 없게 한다. 소비자는 중복 수신을 견딘다(멱등).
- 이벤트가 필요 없는 곳에 이벤트를 만들지 않는다. 같은 모듈 안의 동기 호출로 충분하면 직접 호출한다.

### 서비스와 리포지토리

- 도메인 서비스: 특정 엔티티에 자연스럽게 속하지 않는 도메인 규칙(두 계좌 간 이체 규칙). 상태가 없고 도메인 언어로 이름 짓는다. 엔티티에 둘 수 있는 규칙을 서비스로 빼면 빈약한 모델이 된다.
- 애플리케이션 서비스(유스케이스): 하나의 사용자 행위를 조율한다. 로딩 → 도메인 메서드 호출 → 저장 → 이벤트 발행 → 결과 반환. 규칙을 직접 판단하지 않고 트랜잭션·권한·IO만 다룬다. 규칙이 여기서 `if`로 자라면 도메인으로 옮긴다.
- 리포지토리: 애그리거트 하나당 하나. 루트 단위로 저장·조회하는 컬렉션처럼 보인다. 내부 엔티티 단위 리포지토리, 범용 `find(where)` 쿼리 빌더 노출을 만들지 않는다. 읽기 전용 조회 화면은 리포지토리를 우회하는 전용 조회 모델로 단순하게 만들 수 있다.
- 팩토리는 생성 불변식이 복잡할 때만 둔다. 생성자로 충분하면 만들지 않는다.

### 도메인은 프레임워크를 모른다

비즈니스 규칙은 순수 도메인 코드에, IO·HTTP·ORM·메시징은 경계 어댑터에 둔다. 도메인 테스트는 IO 없이 돈다. 저장소 관례가 ORM 엔티티를 도메인 모델로 겸하는 것을 허용하면, 규칙이 그 클래스의 도메인 메서드에 모여 있고 영속 세부가 시그니처로 새지 않는 한 따로 복제 모델을 만들지 않는다. 복제 모델과 매핑 계층은 비용이며 실제 분리 필요가 있을 때만 든다.

## 5. 모델링 세션 절차

새 도메인·새 개념을 다루거나, 용어가 흔들리거나, 규칙이 여러 곳에 흩어진 것이 보이면 구현 전에 밟는다. 인텐트 인터뷰(인텐트 정본)와 같은 세션에서 할 수 있다.

1. 사건부터 모은다. 이 영역에서 일어나는 도메인 이벤트를 과거형으로 시간 순서대로 나열한다. 각 이벤트를 일으키는 명령, 명령을 내리는 행위자, 이벤트에 반응하는 정책("결제가 실패하면 주문을 보류한다")을 붙인다.
2. 불변식을 모은다. 명령이 거부되어야 하는 조건을 적는다. 같은 불변식을 지키는 명령들이 모이는 곳이 애그리거트 후보다.
3. 용어집과 대조한다. 새 단어가 기존 용어와 충돌하거나 한 단어가 두 뜻이면 즉시 드러내고 어느 뜻인지 정한다. 모호한 단어는 정확한 후보 용어를 제안해 확정한다.
4. 시나리오로 경계를 때린다. "부분 환불 뒤 주문을 다시 확정하면?", "같은 쿠폰을 두 주문에 동시에 쓰면?"처럼 구체 엣지 시나리오로 개념 사이의 경계를 강제한다. 답이 갈리면 컨텍스트나 애그리거트 경계가 흐린 것이다.
5. 코드와 대조한다. 기존 코드가 설명과 다르게 동작하면 그 모순을 드러내고 어느 쪽이 맞는지 정한다. 추측으로 한쪽을 고르지 않는다.
6. 즉시 기록한다. 확정된 용어는 그 자리에서 용어집에, 컨텍스트 관계는 구조 지도에, 되돌리기 어려운 모델 결정은 인텐트의 `결정`에 남긴다. 세션 끝에 몰아 적지 않는다.

사람만 답할 수 있는 도메인 질문(비즈니스 규칙의 진실)은 추측하지 않고 인텐트의 열린 질문으로 올린다.

## 핑계와 반박

| 핑계 | 반박 |
|---|---|
| "이름은 나중에 맞추면 된다" | 코드에 먼저 박힌 이름은 API·DB·화면으로 퍼진다. 나중 rename은 전 표면 이관이다 |
| "user든 account든 다 아는 말이다" | 두 단어는 두 개념으로 읽힌다. 다음 사람은 차이를 찾느라 시간을 쓰고, 결국 차이가 생긴다 |
| "검증은 호출하는 쪽에서 하면 된다" | 호출자가 늘면 하나는 빠진다. 불변식은 소유자 한 곳이 지킨다 |
| "관련 있으니 같은 애그리거트에 넣자" | 관련성이 아니라 즉시 정합이 필요한 불변식이 경계를 정한다. 거대 애그리거트는 경합과 느린 로딩을 부른다 |
| "DDD니까 리포지토리·팩토리·서비스 계층부터 깔자" | 규칙 없는 CRUD에 계층을 깔면 간결성 위반이다. 규칙이 생길 때 모델로 끌어올린다 |
| "다른 팀 테이블을 직접 읽는 게 빠르다" | 보이지 않는 공유 커널이 생긴다. 그 팀의 스키마 변경이 예고 없이 나를 깬다 |
| "금액은 그냥 number로 충분하다" | 통화·반올림·정밀도 규칙이 호출부마다 흩어진다. 값 객체 하나가 그 규칙의 소유자다 |

## 위험 신호

- 같은 개념에 둘 이상의 이름, 용어집에 없는 도메인 단어가 코드에 등장
- `setStatus`·`update`·`process`처럼 도메인 동사가 아닌 메서드가 규칙을 대신함
- 같은 불변식 검사가 여러 서비스·컨트롤러에 반복
- 규칙이 애플리케이션 서비스의 `if`로 자람, 엔티티는 getter/setter만 가진 빈약한 모델(규칙이 있는 영역에서)
- 객체 참조로 엮인 애그리거트, 한 트랜잭션에서 여러 애그리거트 수정
- 다른 컨텍스트의 내부 모델 import, 다른 컨텍스트 테이블 직접 접근
- 금액·시각·식별자의 원시 타입 사용
- 규칙 없는 영역에 깔린 전술 패턴 계층, 미리 만든 팩토리·리포지토리 인터페이스
- 일반 하위 도메인을 직접 구현, 핵심 하위 도메인을 프레임워크 기본값에 위임
- 용어집에 구현 세부·작업 메모가 섞임

## 종료 게이트

- [ ] 이번 작업의 개념마다 용어집의 한 단어가 있고, 코드·테스트·UI·문서가 같은 단어를 쓴다(금지 동의어 grep 0건)
- [ ] 적용 강도를 판정했고, 그 강도를 넘는 패턴을 만들지 않았다
- [ ] 각 불변식의 소유자가 정확히 하나이고, 위반 시도를 거부하는 테스트가 있다
- [ ] 애그리거트를 만들었다면 루트 외 접근 없음, 다른 애그리거트는 ID 참조, 트랜잭션당 하나
- [ ] 컨텍스트가 여럿이면 컨텍스트 맵이 구조 지도에 있고, 경계를 넘는 import·테이블 접근이 없다
- [ ] 이벤트를 만들었다면 저장과 발행의 원자성, 소비자 멱등성을 테스트로 확인했다
